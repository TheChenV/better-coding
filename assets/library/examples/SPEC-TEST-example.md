## 为什么这份长这样

测试计划不是用例清单的目录，而是**判达标的尺**：阈值、工具、
级别、触发点四样一起写，缺一就无法在环节 7 直接执行。
每个端点都要有正向 / 异常 / 边界三类，只列 happy path 的计划等于
把最贵的缺陷留到线上。

## 片段 3 · 6.1 测试风险：写"假绿灯"怎么来的

```markdown
| 风险 | 影响 | 缓解 |
|------|------|------|
| Mock 与真实 API 漂移 | 全绿但线上炸（假绿灯） | 契约 Schema 进 CI，YAML 变更触发生成 |
| 支付回调超时难模拟 | E2E 慢且不稳 | 用可控时钟推进超时，不靠 sleep |
| 用例数据残留 | 相互污染、偶发失败 | 每 suite 独立事务 + afterEach 回滚 |
| Token 刷新竞态 | 并发下重复刷新 | 专项并发用例：10 并发同时 401 |
```

## 最容易走形的三处

1. 阈值写成"覆盖率尽量高"——无数字、无工具、无触发点，无法判。
2. P0/P1 用户故事没有全覆盖（PRD 里 6 条 P0，这里只覆盖 4 条）。
3. 异常用例只断言状态码，不断言副作用真的发生（支付失败要断订单已回滚）。
