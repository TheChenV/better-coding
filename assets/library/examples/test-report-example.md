# 示例 · 测试报告（环节 7 执行结果 + 上线结论）

> 无固定模板文件：结构以 `/run-tests` Step 4 的产出契约为准
> 落盘：`docs/test/spec-shop-web-测试报告.md` ｜ 依据：`SPEC-TEST` 全部用例
> 结论一律用用户语言：可以上线 / 不建议上线、必修项、已接受的风险、回滚方案。

## 为什么这份长这样

报告的作用不是"报通过率"，而是**让签字的人能做决定**：
每个未达标项要点名到用例、给出根因、给出处置与耗时估算。
只报绿不报漂移，等于把契约不一致推到线上。

## 章节骨架

```
报告头（执行日期 / 环境与启动方式 / 依据的测试计划路径）
1 执行概览    分层统计：单元 / API 契约 / E2E，含跳过与待实现列
2 覆盖率      阈值行 + 模块明细
3 E2E 结果    按 spec 文件列场景与用例数
4 API 与契约结果  通过项 / 漂移项（当前 vs 契约要求）/ 待实现（谁的责任）
5 修复与根因  本轮修掉的缺陷：现象 → 根因 → 影响文件
6 检查点判定  逐条对照 SPEC-TEST 第 4 章，含未通过项
7 结论与处置  可以上线 / 不建议上线 + 必修项 + 已接受的风险 + 回滚方案
8 后续行动    优先级 / 动作 / 负责方 / 预估耗时
```

## 片段 2 · 4.2 契约漂移：当前值与要求值并排放

```markdown
全部集中在 M-01 商品浏览模块，Mock 用 camelCase，契约要求 snake_case：
| # | 问题 | Mock 当前 | 契约要求 |
|---|------|----------|---------|
| 1 | SPU 字段名 | `spuId`, `imageUrl` | `spu_id`, `main_image` |
| 2 | 分页结构 | 扁平 `{items,total,page}` | 嵌套 `{items, pagination:{page,total}}` |
| 3 | 详情结构 | 扁平 + `attrs` | 嵌套 `spu` 对象 + `attributes` |
其余模块（购物车 / 订单 / 支付 / 认证）与契约一致，0 diff。
```

## 片段 3 · 6 检查点判定 + 7 结论：不达标就写不建议上线

```markdown
| 指标 | 阈值 | 当前 | 判定 |
|------|------|------|------|
| 单元分支覆盖率 | ≥ 80% | 92.18% | 通过 |
| E2E P0 通过率 | 100% | 100%（10/10） | 通过 |
| API 契约一致性 | 0 diff | 6 diff | **未通过** |
| 安全扫描 | 0 Critical | 未执行 | 待补 |

**结论：不建议上线**（商品模块契约漂移阻塞，必修项 1 条）。
- 必修项：修 Mock handler 的 6 处命名与结构，估 0.5 天（前端）。
- 已接受的风险：`guards` 模块分支覆盖 50%，仅影响降级路径，已记风险台账。
- 回滚方案：本次仅前端静态资源，回滚 = 切回上一版本 CDN 目录，1 分钟内可完成。
```

## 最容易走形的三处

1. 把跳过的 6 条用例删掉了事 → 报告里看不到"为什么没测"。
2. 失败只写"用例不通过"，无根因与影响文件 → 下轮同款缺陷再来。
3. 结论写"总体还行"：没有必修项清单、没有回滚方案，无法签字。
