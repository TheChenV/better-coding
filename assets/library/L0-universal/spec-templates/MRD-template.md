> **文档编号**: MRD-[项目编号]-[序号]
> **版本**: v0.1
> **状态**: 草稿 | 评审中 | 已批准（三值由该步自检清单驱动：清单全过即写"已批准"，由产出方落盘时直接写，不等用户口令）
> **作者**: [姓名]
> **创建日期**: [YYYY-MM-DD]
> **最后更新**: [YYYY-MM-DD]

> **文档定位**: MRD 位于 PRD 和技术规格的上游，衔接业务战略与产品规划。它回答"为什么做、为谁做、期望什么商业结果"，为下游团队提供经过验证的启动依据。
> **边界声明**: 本文档**不覆盖**功能细节、用户交互流程、验收标准、系统架构、数据模型或接口契约 — 这些属于 PRD 和技术规格文档。
> **统一 MRD 原则**: 多应用（如中台 + 商城 + 管理后台）合并为**一份统一 MRD**，不按应用各写一份。MRD 是平台级唯一上游真相源，下游按应用维度拆分 PRD。

> **MRD 严禁写清单（越界即删）**:
> - ❌ 技术选型（Spring Boot / React / MySQL 等）→ 留给 ARCH
> - ❌ P99 / SLA / RTO / RPO 等性能数字 → 留给 ARCH
> - ❌ API / DTO / 错误码 → 留给 PRD / SPEC
> - ❌ 模块拆分 / 架构分层 → 留给 ARCH
> - ❌ QPS / DAU 的精确容量规划 → 仅写方向级规模（"预期 DAU ~50K"可以，"P99 ≤ 200ms @2000QPS"不可以）
> - ✅ 只写：业务目标、规模方向、能力域、跨应用契约（能力级）、MVP 范围

## MRD vs PRD vs SPEC 责任矩阵

| 维度 | MRD | PRD | SPEC |
|------|-----|-----|------|
| 核心问题 | Why, for whom, what business outcome | What to build, acceptance criteria | How to implement, technical constraints |
| 粒度 | 市场/战略/方向级 | 功能/场景/验收级 | 架构/模型/接口级 |
| 主要作者 | 业务/产品负责人 | 产品经理 | 架构师/技术负责人 |
| 包含 | 市场机会、目标用户、方案方向、商业目标 | 功能清单、用户故事、交互流程、验收标准 | 领域模型、服务拆分、数据模型、API 契约 |
| 不包含 | 功能细节、交互设计、技术栈、数据结构 | 代码实现、DDL、部署拓扑、接口字段 | 市场分析、商业模式、用户调研 |
