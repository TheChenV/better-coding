# Spec 先行原则

> 来源：GitHub Spec-Kit + Superpowers brainstorming — Spec 是第一公民，代码是规格的产物。
> v8.5.0 起并入原 `documentation-sync` 规则的文档同步义务（两条规则的"以 Spec 为准"引导语本为严格子集关系）。

## 强制规则

1. **任何功能实现前必须有对应的 Spec 文档**（MRD/PRD/ARCH/SPEC-BE/SPEC-FE 中的至少一个）
2. **无 Spec 的代码变更必须补充 Spec** — 先补文档，再写代码
3. **Spec 与代码不一致时，两个出口并列且只有这两个** — 以 Spec 为准修正代码，**或**走 Spec 变更流程改 Spec；禁止"悄悄改 Spec 让它适配代码"
4. **Spec 变更必须走变更流程** — 变更单独立留痕（`/spec-delta`），不能与代码改动混为一次提交

## 文档同步义务（原 `documentation-sync`，v8.5.0 并入）

1. **代码变更必须同步更新相关文档** — 改了 API 就更新 API 文档
2. **文档滞后不得超过一个迭代** — 每个迭代末检查文档与代码的一致性
3. **CHANGELOG 必须随版本更新** — 每个发布版本记录变更内容

| 代码变更 | 需同步的文档 |
|---------|------------|
| 新增/修改 API | OpenAPI/Swagger 文档 |
| 新增/修改数据表 | DDL 文档、数据字典 |
| 修改业务规则 | PRD 中对应的 User Story |
| 修改架构 | ARCH 文档、ADR |
| 修改配置 | 部署文档、环境变量说明 |
| 项目结构变更 | AGENTS.md |

**活文档节奏**：每次代码变更同步相关 Spec/API 文档 → 每次迭代末查一致性 → 每次发布前全面文档审查。

## 检查清单

- [ ] 每个新增 API 端点都有对应的 SPEC-API 定义
- [ ] 每个新增数据表/字段都有对应的 SPEC-DDL 定义
- [ ] 每个业务规则都有对应的 PRD User Story
- [ ] 代码实现可追溯到 Spec 中的具体条目
- [ ] 本轮改动涉及的文档（上表命中项）已同步，滞后未超过一个迭代

## 规格生命周期（活规格 + 变更增量）

- `docs/spec/` 是**权威活规格**：长期维护、始终描述"系统现在是什么"，不是某次迭代的快照
- `docs/changes/` 放**提案与增量**（delta）：一个变更一个文件夹，实施完成即 archive 合并回 `docs/spec/`，不长期堆积
- `docs/prd/` 与 `docs/arch/` 是**决策留痕**：记录当时为什么这么定；后续改动走变更增量，**不每次需求都重画全量 PRD/ARCH**
- 判据：同一件事在两处各写一份全文 = 双源，必须收敛为一处权威 + 另一处引用

## 豁免条款（v4.0.0）

- `/quick-spec` 快速通道产出的 `docs/spec/QUICK-*.md` 视为合法 Spec（适用于满足准入条件的小改动）
- 紧急生产修复（hotfix）可先修复，但必须在 24 小时内补齐 QUICK spec 或正式 spec

## 违规处理

- 无 Spec 的代码变更 → 暂停实现，先补 Spec
- Spec 与代码不一致 → 以 Spec 为准修正代码，或走 Spec 变更流程
- 文档滞后超过一个迭代 → 本次迭代内补齐，不得顺延到下个迭代
