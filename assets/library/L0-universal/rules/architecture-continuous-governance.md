# 架构持续治理

> 来源：Matt Pocock improve-codebase-architecture + Harness 课程第 7 课 — 架构腐化是累积的，治理也必须是持续的。

## 强制规则

1. **每次涉及跨层变更时必须检查分层依赖方向** — 禁止反向依赖
2. **新增模块必须符合 ARCH 中定义的分层架构** — 不允许引入新的层次
3. **对象类型数量不超过 5 种** — Entity + Request + VO 为基础，超过 5 种必须审查
4. **继承深度不超过 3 层** — 超过 3 层必须用组合替代
5. **接触即迁移** — 修改遗留模块时必须同时迁移到新架构

## 架构腐化信号

| 信号 | 阈值 | 行动 |
|------|------|------|
| 继承深度 > 3 层 | 立即审查 | 用组合替代继承 |
| 对象类型 > 5 种 | 立即审查 | 精简对象体系 |
| 单文件 > 500 行 | 立即审查 | 按职责拆分 |
| 单函数 > 50 行 | 立即审查 | 提取子函数 |
| 分层违规 | 立即修复 | 恢复依赖方向 |

## 治理节奏

- **每次变更**：检查分层依赖方向
- **每次迭代末**：运行 `/architecture-governance` 架构合规检查
- **每次代码审查**：关注架构偏离

## 违规处理

- 分层违规 → 立即修复，不可作为技术债务延期
- 对象类型超标 → 本迭代内精简
- 遗留模块修改未迁移 → 补充迁移
