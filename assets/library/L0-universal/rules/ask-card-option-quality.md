# 选择卡契约 v10

平台事实（取证与证据级以 `/platform-profile` §六 为唯一权威源，本段是其执行摘要，改平台先改那边）：`options[].label` **会渲染**，是选项行唯一的主色字段；`description` 同行弱色、**单行截断**、且**永不回传给模型**；答完后模型收到的 `tool_result` **只含 label**。「推荐」徽标由平台**硬编码挂给第 1 个选项**。行首徽标是数字 1/2/3/4 且可键直选；`header` 不进可见 DOM，`preview` 不渲染，`question` 最多 3 行。

## 六条硬规则

1. `label` = 具体候选值，名词短语，≤16 字，禁止评价性文字；超长时**截评价不截值**。
2. 推荐项**必须排在第 1 位**；label 内**不写**「（推荐）」等标记——平台已自动挂徽标，再写就是两个相反信号。
3. `description` = `{量化影响}；{推荐理由}`，≤40 字（一行读得完），**不得以 label 原文或【label】开头**，重复即违规。
4. `question` 只写问题本身，≤2 行，**不追加值清单**。
5. `options` 2–4 个（工具硬约束）；每批 ≤4 问，但平台一次只显一题。
6. 渲染分两阶段：先落中间态四字段（候选值 / 量化影响 / 推荐理由 / 是否推荐），再按上五条映射；渲染后逐选项回问「label 是不是一眼可区分的具体值」。

## 为什么纪律反而更硬

v9 曾认定「label 不渲染」，于是把候选值抄进 description 前缀与 question 末尾清单。事实相反：**候选值只有写进 label 才同时被用户看见、被模型记住**。写进 description 的值，用户读到一次，就永久留在模型的记忆之外。

## subagent

subagent 上下文不含本规则，且其工具表面**没有 `AskUserQuestion`**——选择卡只能由主会话发。派遣子任务要候选时，令其返回结构化文本，由主会话发卡。

## 降级

用户报告看不到选项值，或在「其他」里重打完整候选值 → 视为工具不可用，改文本编号式：`Q2-A 纯 Markdown 源码编辑器路线：…`，每个编号项以候选值开头。

机械兜底：`ask-card-guard` PreToolUse hook（H1–H7 结构启发式 + H10 重复 + H11 推荐标记 + H12 超长 + H13 v9 清单残留）。
