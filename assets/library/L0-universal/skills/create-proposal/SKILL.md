# 需求提案生成（环节 1：需求分析）

## 核心理念

> **编码前对齐是最高 ROI 的实践。** 不要拿到需求就开始写方案。先把决策树问透，再落盘结构化需求。
> "AI 以为你要 A，实际你要 B" 是返工的最大来源。
>
> 追问机制对齐开源社区 grilling 引擎（mattpocock/skills）：设计树 + 前沿（frontier）一轮问完 + 每问附推荐答案 + 事实自查不抛给用户。
>
> **选择卡纪律（红线）**：本技能所有 `AskUserQuestion` 遵守**契约 v10**——候选值写进 `label`、推荐项置首、`description` 不重复 label 且 ≤40 字、`question` 不附值清单。唯一权威源 `.qoder/rules/ask-card-option-quality.md`；机械兜底 `ask-card-guard` hook。
>
> **多步骤模型**：环节 1 = 步骤① idea→MRD（多专家并行）· 步骤② MRD→按应用多份统一 PRD · 步骤③ PRD→交互原型工程（仅 Full-Stack）。三步严格串行：MRD 定稿才产 PRD，PRD 定稿才产原型。

## 定位与分工

- **本技能**：新需求轻量澄清——把一句话想法变成结构化需求，无代码库依赖
- **`/precode-alignment`**：有代码库/文档基础的深度对齐（grill-with-docs 定位），产出决策记录
- 两者共用同一套前沿式追问纪律（见 Step 1B）

## 产出契约（强制，环节卡为单一契约源）

| 项 | 契约 |
|----|------|
| 产出物 | `docs/prd/MRD-{项目代号}.md`（统一 MRD，多应用合并一份，**独立冻结**）+ `docs/prd/PRD-{应用}.md`（每应用一份统一 PRD，拒绝文档级拆分）+ `docs/prd/PRD-{应用}-交互原型/`（仅 Full-Stack，可运行工程目录）——**MRD + PRD 缺一不可，Full-Stack 原型必须** |
| 模板依赖 | `docs/harness-templates/MRD-template.md`、`docs/harness-templates/PRD-template.md`（产出前必须读取模板结构，按其章节组织内容） |
| 归档位置 | `docs/prd/`（扁平布局；禁止落到其他目录） |
| 附带写回 | 词汇本（`.qoder/rules/project-domain-glossary.md`，新确认术语当场登记）+ PROJECT-LIVE.mddocs/项目交接.md（任务启动即建）+ `.qoder/harness-profile.json` 的 `appType`（Backend-Only / Full-Stack）与 **`project.apps`（v9.10.0：应用清单唯一权威，逐应用 `{name,type,source}`）** 与 `mrdPanelMode`（full / lite / frontier）与 `skipPrototype`（true / false）与 `mrdPanelSize`（N）与 `mrdPanelRoles`（角色清单） |
| 收尾 | 执行 3 步同步（唯一规范：`.qoder/commands/live-refresh.md`） |

## 触发条件

- 用户输入 `/create-proposal`（或 `/propose`）
- 用户提出新项目想法或新功能需求，且尚无 PRD
- PROJECT-LIVE.md 提示词手册的环节 1 入口

## 执行步骤

## 两条不可协商的约束（语料回灌，v9.0.0）

1. **发散-收敛循环必须跑满 5 轮**（不是"直到没新东西"）。5 轮里每轮都要留下增量结论；
   不足 5 轮就出文档，视为本步未完成，不得进入下一环节。
   为什么是硬次数而不是"够了就停"：AI 倾向尽早收敛并给出看似完整的答案，轮数是唯一能核对的过程证据。
2. **追问必须一次一问，且每问先给推荐答案**：一次只问一个问题，问题里带上候选、代价与建议选项；
   禁止一次抛一串问题让用户填表——那样用户会挑着答，剩下的被 AI 自行补齐（本库最常见的返工来源）。

自检：以上两条各自可在产出里核对（轮次记录写在 MRD 附录；追问记录写在项目交接的已决策小节）。

### Step 0: 应用类型分类

> **在任何追问之前，先确认应用类型。此信息决定后续步骤的分支路径。**

1. **判定应用类型**：根据用户描述判定为 `Backend-Only` 或 `Full-Stack`
   - **Backend-Only**：仅暴露 REST/gRPC 接口，无前端层
   - **Full-Stack**：包含前端层（SPA/SSR）和后端层，独立部署
2. **多应用场景**：若系统包含多个应用（如中台 + 商城 + 管理后台），逐应用声明类型
3. **写回 profile**：将 `appType` 写入 `.qoder/harness-profile.json`（单应用直接写值），并**同时**写 `project.apps`（v9.10.0 起应用清单的唯一权威源）：每个应用一条 `{ "name": "应用名", "type": "Backend-Only | Full-Stack", "source": "MRD 章号 + 日期" }`；**单应用也要写成一条**。（旧文档里的 `appTypes: { "应用名": "类型" }` 从未实现、无读者，作废）
4. **下游影响**：
   - `Backend-Only` → Step 4.5 跳过（置 `profile.skipPrototype=true`，进展图标 ⊘）；PRD 跳过 Section4 交互流程
   - `Full-Stack` → Step 4.5 必须执行；PRD Section4 必填
5. **未确认前**：以选择卡确认（推荐 Full-Stack，除非用户明确说"纯后端"）

### Step 1A: 多专家并行产出 MRD（可配置）

> **主 Agent 兼任 TL，同轮并行派遣 N 位领域专家独立 subagent 分析，产出统一 MRD。**
> 「并行派遣」在本版 App 上没有专家面板：由主会话用 `Agent` 工具在同一轮内派生 N 个 subagent，角色设定随提示词内联；两条边界（subagent 无 `Agent` 不能再嵌套派生、无 `AskUserQuestion` 不能向用户发卡 → 拍板一律回主会话）见 `skills/platform-profile/SKILL.md` §一。

#### 候选池三参数（v9.6.0：默认名单是候选池，不是配额）

| 参数 | 说明 | 默认值 | 护栏 |
|------|------|--------|------|
| `{专家数量}` N | 本步**实派**领域专家数 | 按项目形态在 3-6 内选定（默认候选池 6 位） | 3 ≤ N ≤ 6 |
| `{专家种类清单}` | 各专家关注领域 | 产品/架构/业务/运营/安全/测试（可增/删/换） | 至少含产品+架构 |
| `{MRD补充指令}` | 额外业务约束或特殊要求 | 无 | 自由文本（并入下方 Q1 的"其他"输入，不单独发卡） |

#### 配置确认（选择卡，一批 ≤4 问；v9.6.0 起合并为两问）

- **取值优先级（v9.6.0 裁决，替掉 v8.4.0「提示词显式给出时以提示词为准」与 v9.0.0「执行时以 profile 裁剪」这对互斥表述）**：
  `本次会话用户选定的方案` ＞ `profile.mrdPanelSize / mrdPanelRoles 有值（用户此前声明过 → 直接采用，不再问）` ＞ `默认候选池（本文件「默认面板」表）`。
  手册 1·1 提示词里内联的 6 位是**候选池**——用户必须看得见有哪些角色可挑，但这句话不构成"必须派 6 位"的指令。
- **Q1 分配方案**：AI 先按用户那句话判断项目形态（谁用 / 单应用还是多应用 / 有没有增长与合规负担），给出 **2-3 套方案**同卡呈现：每套写清「实派几位、每位关注点 → 要交出的结论、为什么适配本项目」并标推荐项；讨论深度随方案一并给（完整 7 轮 / 精简 3 轮 → 决定 `mrdPanelMode=full|lite`）；特殊业务约束走本问"其他"自由输入。
- **Q2 项目代号**：给 **2-3 个候选**（含从想法或工作区目录名推导的推荐项），说明它要进 `docs/prd/MRD-{代号}.md`、`docs/arch/ARCH-{代号}.md` 与面板标题；**未确认前不得自定**，用户回「你来起」才算授权。
- **写回闭环**：Q1 结论写回 `mrdPanelSize`/`mrdPanelRoles`/`mrdPanelMode`，Q2 结论写回**既有字段** `profile.project.name`（代号即项目名，面板标题同源，不新增字段）——保证跨会话不重复问。
- **🚫 禁止形态**：把默认名单原样派出去、只在会话里说一句"我把某位的产出重心改了"而不登记。这是 v9.6.0 实测抓到的漂移（AI 因两条权威互斥而自创的第三条路），堵法见 `.qoder/briefing-skeletons.md` §五 护栏 (b)。

未声明参数（且 profile 也无值）→ 使用默认候选池全 6 位，并在 MRD 头部标注 `<!-- 多专家并行配置：N=6（默认候选池全用）, 深度=7轮(full), 补充指令=无, 项目代号=<Q2 确认值> -->`；**实派名单与默认候选池不同 → 该行改为实际名单 + 每位关注点 + 增删理由**（护栏 (b) 的登记面）。

#### TL 与执行机制（编排五要素）

- **①命令前缀**：`/create-proposal`
- **②编排指令**：TL=主 Agent（执行本 skill 的会话主体，负责分配任务、组织讨论、收敛结论）；全部专家 Agent 调用同一轮发出、不嵌套、独立上下文（对齐环节 6·1 与 7·2 的并行派发范式——主 Agent 编排多 subagent）；专家以独立 subagent 并行运行（`dispatching-parallel-agents`），每专家从自身视角分析需求并输出结构化草稿
- **③每专家设定**：默认候选池 6 位的用户可见副本内联在骨架 1·1 提示词中（权威源 = 下方「默认面板」表；**v9.6.0 口径**：内联那份是**可挑的候选池**，不是配额——实派名单由 Q1 用户选定，按上方取值优先级裁决）。**派遣前必须先过 Q1：用户没选定方案前不派遣任何专家**；表外自定义角色由主 Agent 即时合成一行设定（沿用本表“关注点/主要产出/输出结构”三列结构）并在 MRD 头部标“待确认”，禁编造项目事实
- **④grill-me 卡点**：每问 ≥2 候选 + 量化影响 + 推荐项；选择卡契约以 `.qoder/rules/ask-card-option-quality.md`（契约 v10）为唯一权威源，机械兜底 = `ask-card-guard` hook（H1-H7 + H10-H13）
- **⑤主 Agent 合并落盘**：专家只读产草稿，MRD 由主 Agent（持 Write）统一落盘后执行 3 步同步
- **交互纪律显式下发**：派遣各领域专家 subagent 时，**必须在其 prompt 中显式写入**：
  1. 「本技能所有需要用户决策的点，子任务**只返回结构化候选**（候选值 / 量化影响 / 推荐理由 / 是否推荐），不要试图向用户提问」——subagent 的工具表面没有 `AskUserQuestion`，试图发卡会直接失败；发卡一律由主会话执行
  2. **四字段中间态强制步骤**：每个决策点先交齐四个字段，主会话再按契约 v10 渲染成选择卡（渲染细则见规则文件，不在此复述）
  subagent 上下文不含主会话规则，不显式下发等于规则不存在（参照 create-module-spec 对 API 约定"subagent 模式下显式读入防漂移"的处理）

#### 默认面板（候选池，v9.6.0 起不再是"兜底配额"）

> **v9.6.0 双源口径改写（替 v8.4.0「提示词显式给出时以提示词为准」）**：骨架 1·1 提示词内联的 6 位 = **用户可见、可挑的候选池**（看不见就没法改，这一点 v8.4.0 的判断保留）；实派名单由 Q1 用户选定，优先级见上方「取值优先级」三档。
> **护栏 (b) 换形（原「内联关注点措辞必须逐字复制本表」）**：该护栏**实测早已空转**——2026-09-11 逐行比对骨架 `:149-154` 与本表，**6/6 行措辞都不一致**（例：骨架"目标量化"vs 本表"业务目标量化"；骨架"合规、数据安全…"vs 本表"合规要求、数据安全…"），且 `harness-verify` 只用 Check 7g 断言 6 个**专家名**在场，无任何判据守措辞。故本批改判"文本对齐"为**登记对齐**：未增删时沿用本表措辞；**任何增/删/改写过的角色，必须在 MRD 头部逐字登记实际用的关注点与理由**（登记物是落盘产物，可机检；靠两份文本互抄则永远会漂）。
> **候选池**：6 位（产品/架构/业务/运营/安全/测试）；`profile.mrdPanelMode`/`mrdPanelSize`/`mrdPanelRoles` 可收窄/自定义（收窄下限 3 且至少含产品+架构）；lite/frontier 档裁剪见下方 token 三档；专家 subagent 只读产草稿（无 Write），MRD 落盘由主 Agent 统一执行；表外角色以本表三列结构（关注点/主要产出/输出结构）为合成基准并标"待确认"。

| 专家 | 关注点 | 主要产出 | 输出结构 |
|------|--------|----------|----------|
| 产品专家 | 用户价值、业务目标量化、功能优先级、MVP 边界 | 战略陈述/用户画像/MVP In-Out 清单 | 结论3-5条+依据+待裁定项 |
| 架构专家 | 系统边界、依赖可行性、实现风险与成本量级（只判能不能做，不出选型方案与模块拆分） | 应用拆分建议/能力域/依赖契约草案/高风险需求清单 | 结论+Provider↔Consumer 对称表 |
| 业务专家 | 业务规则完整性、异常场景覆盖、业务模型闭环 | 业务规则/异常场景清单 | 规则条目+异常分支+开放问题 |
| 运营专家 | 运营抓手、数据指标体系、增长策略、成本管控 | ≥3项量化目标/指标体系 | 目标表（指标/基线/目标值）+增长假设 |
| 安全专家 | 合规要求、数据安全、支付安全、攻击面 | 合规约束/敏感数据范围 | 约束条目+风险等级+缓解建议 |
| 测试专家 | 可测性、验收标准、端到端场景、边界条件 | ≥5个端到端场景/验收要点 | 场景G/W/T摘要+边界清单 |

#### token 三档（`profile.mrdPanelMode`）

| 档位 | 触发条件 | 配置 |
|------|----------|------|
| `full` | 默认/Q1 方案含 7 轮 | MRD 6专家+7轮；PRD 精简4专家（产品/架构/业务/测试） |

### Step 1B: 前沿式追问收敛（idea-refine + grill-me）

> **在多专家并行产出草稿后，通过多轮发散收敛 + 关键争议澄清，确保需求完全对齐。**

#### idea-refine 7轮议程

| 轮次 | 焦点 | 收敛产出 |
|------|------|----------|
| 第 1 轮 | 战略主题 / 核心矛盾 | 1 句战略陈述 + 主要矛盾 |
| 第 2 轮 | 市场机会 / 竞品 | ≥3 家竞品对比表 + 切入点 |
| 第 3 轮 | 目标用户 | ≥2 类角色含画像/诉求/场景 |
| 第 4 轮 | 规模与成功度量 | DAU/QPS/转化率等 ≥3 项量化目标 |
| 第 5 轮 | 三层架构与能力域 | Provider/Consumer 边界 + 能力域清单 |
| 第 6 轮 | Phase 1 MVP 范围 | In-Scope / Out-of-Scope 清单 |
| 第 7 轮 | 跨应用依赖契约 | 能力级（非 API 级）双向对称 |

**精简模式（`lite`）**：仅保留第 1/3/6 轮（战略→用户→MVP），跳过其余。

#### grill-me 关键争议澄清

- **触发条件**：存在多候选且无明显优劣的决策点
- **格式要求**：每问 ≥2 候选 + 量化影响；**生成选项前必须先完成四字段中间态**（候选值/量化影响/推荐理由/是否推荐），再按契约 v10 映射为 label 与 description
- **交互形态调和**：
  - **关键争议**（影响架构/商业模式/能力域边界）→ 逐条问，每条给出 ≥2 候选 + 量化影响对比；**若用选择卡承载，同样按契约 v10 三件套写**
  - **常规前沿**（命名/优先级/范围微调）→ 批量选择卡（≤4 问一批，沿用交互方式纪律）
- **循环口径**：**"前沿为空即止"**（设计树所有分支走完、无静默假设）——**不写死固定轮次**
- **grill-me 不是闲聊**：每次提问必须给出 ≥2 候选 + 量化影响，候选值写进 `label`、量化影响与理由写进 `description`（契约 v10），禁止让用户盲选

#### 机制（对齐官方 grilling 引擎）

1. **设计树**：把需求映射为一棵决策树——每个决策分支出依赖它的后续决策
2. **前沿（frontier）**：所有"前置已定、现在就能问"的未决决策点。**一轮把当前前沿全部问完**，不要挤牙膏式一次一问；**禁止把超过 4 个问题用纯文本一次性长文抛出**（交互方式见下方纪律）
3. **每问格式**：编号 + 选择题（可选多选）+ **推荐答案** + 推荐理由。大多数问题用户点选/回一句"同意"即可推进
   ```
   ❓ **Q1** - **积分过期策略**：固定周期清零还是滚动过期？
   ➡️ 推荐：滚动过期（实现简单、用户感知公平；依据：同类社区平台常见做法）
   ```
4. **先自查纪律**：**查找事实是你的职责，不是用户的**。可从代码/文档/AGENTS.md/profile/词汇本推导的答案，以"初步结论 + 证据"直接呈现请用户确认，不得抛问；需要探索的事实（读文件、查目录）并行去做，不阻塞其余前沿问题
5. **回答后重算前沿**：用户回答使新决策解锁 → 进入下一轮。依赖未决问题的留到后续轮
6. **结束条件**：前沿为空（设计树所有分支走完、无静默假设）且用户确认共识达成。**共识达成前绝不产出文档**

#### 交互方式纪律（Qoder 平台适配，强制）

1. **选择卡优先**：追问优先使用宿主的选择卡交互工具（Qoder AskUserQuestion）——用户点选作答，无需手打；**不得把超过 4 个问题用纯文本一次性长文抛出**
2. **分批约束**：每批选择卡 ≤4 个问题、每问 2-4 个选项（工具硬约束）；前沿问题超过 4 个时按依赖关系分组分批发出（答完一批 → 重算前沿 → 发下一批）；同一批内问题必须互相独立，不依赖彼此答案；需要 multiSelect 时启用多选（非互斥决策）
3. **选择卡写法 = 契约 v10**（权威源 `.qoder/rules/ask-card-option-quality.md`，本技能不再复述契约正文；复述即第二事实源，必然漂移）：
   - 本技能落卡前三条自检：`label` 是可区分候选值（≤16 字）？推荐项排在第 1 位、label 内没写「（推荐）」？`description` ≤40 字且不以候选值开头？
   - 工具硬约束照旧：每问 2–4 个选项、每批 ≤4 问（平台一次只显一题）、工具自带「其他」自由输入，无需另设开放题（每批最多 1 个开放题）
   - 命名类决策须在 description 给**落地后果示例**（如 "MRD-blog.md / PRD-blog.md 两份产物同名前缀"），这是 v10 之外的本技能特要求
   - 正误示例（实测案例，命名类）：
     - ❌ 错误：label=「更简短，但可能与通用博客项目混淆」（把理由当成了值）
     - ✅ 正确：label=「blog」，description=「更简短；代价是可能与通用博客项目名混淆」
   - 正误示例（**技术路线类多候选**，实测案例——长值 + 长权衡如何共存）：
     - ❌ 错误：label=「开发最快、技术用户亲切，但家人等非技术用户上手门槛高，对标语雀体验打折」（权衡写进了 label，值反而没了）
     - ✅ 正确：label=「纯 Markdown 源码路线」，description=「开发最快；代价是非技术用户上手门槛高」
     - 要点：候选都有较长权衡时，**权衡一律进 description，label 只留可区分的方案名**——「每个选项都很长」≠「每个选项都有值」
4. **复杂确认用文本 + 收口卡**：清单式确认（如 MVP 边界清单、详细业务规则）不适合拆成选项时，用文本完整呈现，随后用一张收口选择卡（同意 / 需调整，调整走"其他"说明）收集结论；一次会话最多 1 条文本型确认，避免刷屏式长文
5. **降级条款**：选择卡工具不可用（环境限制/调用失败），或命中**降级三信号**（用户报告看不到选项值 / 用户在"其他"重打完整答案值 / 卡片未按契约携带冗余值）→ 一律视同工具不可用，降级为文本编号式（Q1/Q2/… 选择题 + 推荐答案，支持"Q2 选 A，其余同意"式回复），并在追问开头说明降级原因；**降级为文本编号式时，每个编号项以答案值开头，编号锚点与 `A ·` 惯例统一**（如 `Q2-A 纯 Markdown 源码编辑器路线：开发最快、技术用户亲切，但非技术用户上手门槛高`），不得只写评价

#### 追问预算与出口（诚实纪律）

- 每批/每轮问题数建议 3-5 个（单批选择卡硬上限 4）；预算用完**不得自行补齐剩余决策或直接开工**，等待用户选择是否继续
- 不设硬性轮次上限；但若多轮仍无法对齐（需求本身发散）→ 输出"需求需重新梳理"结论，建议用户先收敛想法，不强行产出
- 用户说"你来定" → 基于项目上下文给出推荐并说明理由，记入"已决策"

#### 必须覆盖的决策维度（映射到设计树主干）

- 需求本质：解决什么问题？不解决会怎样？目标用户与核心痛点？成功标准（可量化）？
- 约束与边界：时间/技术/兼容性/性能约束？
- 范围界定：MVP 包含什么、不包含什么（"本期不做"清单）？
- 决策分支：多种实现路径的偏好？参考产品/竞品？
- 能力域对称：Provider 声明能力域 = Consumer 消费能力域，命名一字不差

#### 追问收敛输出（共识摘要，须经用户确认）

```
需求对齐摘要:
- 核心问题: <一句话>
- 目标用户: <角色>
- 成功标准: <可量化指标>
- 关键约束: <列表>
- 明确不做: <列表>
- 能力域: <Provider声明 ↔ Consumer消费，双向对称>
- 新确认术语: <列表（将写入词汇本）>
- 开放问题: <如有，标注为阻塞项>
```

#### Step 2B: 按应用维度产多份统一 PRD

MRD 冻结后，以 MRD 为唯一上游：

1. **读取模板**：`docs/harness-templates/PRD-template.md`，严格按模板章节组织
2. **应用清单**：根据 MRD 中的系统架构声明，列出所有应用及其类型（Backend-Only / Full-Stack），并**当场写回 `profile.project.apps`**（每条 `{name, type, source: "MRD 章号 + 日期"}`）——下游 `docs/prd/PRD-{应用}.md` 的文件名与提示词里的应用清单值段都从这里取，只在 MRD 正文里叙述而不写回 = 渲染失败
3. **逐应用产出 PRD**：`docs/prd/PRD-{应用}.md`——每应用一份统一 PRD，**拒绝文档级拆分**（不产出 prd-{业务}-业务模块说明.md / 交互流程说明.md 等子文档）
4. **PRD 结构要求**：
   - 每个功能有用户故事；**每个 P0/P1 用户故事至少 2 条 Gherkin 验收标准（Given/When/Then）**
   - US 前缀采用应用维度：`US-{APP}-{NNN}`（如 `US-CART-001`），全局唯一，跨应用不冲突
   - 非功能需求：**ARCH 前向引用**（禁写 P99/SLA/API/DTO，用"详见 ARCH Ch.x"占位）
   - 明确"本期不做"边界清单（防范围蔓延）
   - 末尾记录技术倾向（供环节 2 架构设计参考；技术栈未正式声明时不写入 profile）
   - Full-Stack 应用：Section4 交互流程**必填**（页面清单 + 用户流程 + 关联 US）
   - Backend-Only 应用：Section4 **完全跳过**
5. **多应用并行**：应用间 PRD 互不阻塞可并行写入；Provider（中台）的能力域定义以 MRD 为准

## 实战经验

1. **"我先写 PRD 再说"是最常见的错误** — 不问透就落盘 = 把返工写进文档。先追问，再产出。
2. **推荐答案必须给理由** — 降低用户决策成本；无理由的推荐是耍流氓。
3. **候选值进 label** — 每个 `options[].label` 必须是可区分的具体候选值（名词短语，≤16 字）；推荐项排第 1 位。回传给模型的只有 label，值没写进 label 就等于没提交。
4. **事实自查、决策问人** — 能从环境查到的绝不占用户时间；涉及取舍的必须用户拍板。
5. **模板不是摆设** — 不按模板章节产出 = 下游环节（架构/模块设计）无法按约定消费。
6. **多专家并行 token 护栏** — subagent ≤ 6；`frontier` 档降级为单 agent 前沿式追问；token 耗尽不强行产出半成品。
7. **grill-me 与选择卡形态调和** — 关键争议逐条问（给候选+量化影响）；常规前沿批量选择卡（≤4问一批）；两种形态的**问题组织方式**不混用，但**契约 v10 对两者同等生效**（关键争议若改用选择卡承载，与常规前沿卡写法完全一致：候选值进 label、推荐项置首、量化影响与理由进 description；细则见 `.qoder/rules/ask-card-option-quality.md`，此处不复述）。
8. **统一 MRD 只跑 1 次** — 多应用合并一份 MRD，不按应用各跑一次多专家并行（碎片化 = 契约不对称的根源）。
9. **能力域对称必须当场校验** — Provider 声明 ≠ Consumer 消费 = 契约不对称，必须当场对齐，不留到 PRD 才发现。
10. **MRD 严禁写技术细节** — 出现 API/DTO/P99/SLA/技术选型 → 越界，一律删除或改为"详见 ARCH"前向引用。

## 失败处理

| 失败场景 | 处理方式 |
|----------|---------|
| 需求描述模糊 | 进入前沿式追问，首轮先问主干（本质/用户/成功标准） |
| 范围过大 | 引导砍到最小可用集（MVP），其余入"本期不做"或后续迭代 |
| 多轮仍无法对齐 | 输出"需求需重新梳理"结论，暂停产出，不强行落盘 |
| 术语混用 | 提请用户裁定统一名，写入词汇本后继续 |
| 多专家并行 token 超限 | 降级 `mrdPanelMode=frontier`（单 agent 前沿式追问），不强行派遣 subagent |
| grill-me 争议僵持 | 记录为"开放问题"，标注阻塞项，建议用户线下对齐后回来继续 |
| 选择卡出现盲选项（label 无具体答案值 / description 缺【值】前缀 / question 缺末尾值清单） | 立即重发该批选择卡，不得让用户在信息不全下决策；若被 ask-card-guard hook 拦截，按 stderr 改写示例修正后重发 |
| 能力域不对称 | 当场触发对齐（Provider 优先确认原则），不允许"先往下走" |
| 专家 subagent 无 Write 权限 | 正常——专家 subagent 只读产草稿，MRD 落盘由主 Agent 统一执行 |
