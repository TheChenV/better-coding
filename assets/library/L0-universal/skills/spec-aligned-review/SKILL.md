# 双轴代码审查

## 核心理念

> **不是"帮我看看代码"，而是"按工程纪律做正式审查"。**
> 本 Skill 采用双轴审查模型：
> - **标准轴（Standard Axis）**：代码质量五维度 — 正确性、安全性、可维护性、性能、可读性
> - **规格轴（Spec Axis）**：需求对齐 — 实现是否与 Spec/PRD/ARCH 一致
>
> 来源：Matt Pocock code-review 的双轴模型 + Addy Osmani 的五维审查体系。

## 触发条件

- 用户输入 `/spec-aligned-review`
- 用户输入 `/security-review`（兼容别名：按安全性维度 + 规格轴「安全需求逐条对齐」走，原同名 skill 已并入；OWASP 逐项、密钥泄露、依赖 CVE 审计交给内置 `security-scan`）
- PR/MR 创建后需要审查
- 合并前质量门禁
- 用户要求对某段代码、某个模块或某次提交进行审查

## 执行步骤

### Step 1: 确定审查范围

**必须先明确审查边界，不要上来就看代码。**

```bash
# PR 变更范围
git diff --name-status main...HEAD
git diff --stat main...HEAD

# 或指定文件/目录
git diff --name-only HEAD~3..HEAD
```

**必须收集的信息：**
- 变更文件总数及列表
- 新增/修改/删除行数统计
- 涉及的模块/目录
- 关联的 Spec/PRD/Issue（如有）

**输出审查范围确认：**
```
审查范围:
- 变更文件: N 个
- 新增/删除: +X / -Y 行
- 涉及模块: module-a, module-b
- 关联 Spec: docs/spec/SPEC-xxx.md（如有）
```

### Step 2: 加载审查上下文

**在审查代码之前，先理解"为什么改"。**

1. 读取关联的 Spec/PRD/Issue（如有）— 理解变更意图
2. 读取 AGENTS.md — 理解项目架构约束
3. 读取相关的 `.qoder/rules/` — 理解项目特有规范
4. 如有 ADR，读取相关决策记录

> **实战经验**：不看 Spec 就审查代码 = 只看语法不看意图。很多"看起来有问题"的代码其实是在解决 Spec 中定义的特定业务约束。

### Step 3: 标准轴审查（Standard Axis）

按以下五个维度逐一审查，每个维度独立评分：

#### 3.1 正确性（Correctness）— 权重最高

- 逻辑是否正确，边界条件是否覆盖
- 空指针/未定义引用风险
- 并发安全性（竞态条件、死锁、数据竞争）
- 错误处理是否完整（不吞异常、不忽略错误码）
- 类型安全（是否有隐式类型转换导致的数据丢失）
- 事务边界是否正确

**常见陷阱（实战总结）：**
- `if (data)` 不等于 `if (data !== null && data !== undefined)` — 空值检查要精确
- `for...in` 遍历对象会包含原型链属性 — 用 `Object.keys()` 或 `hasOwnProperty`
- `==` 隐式转换在 JS/TS 中是 Bug 温床 — 一律用 `===`
- Python 的 `except Exception` 会吞掉 KeyboardInterrupt — 用具体异常类型
- SQL 拼接未参数化 = 注入漏洞 — 一律用参数化查询

#### 3.2 安全性（Security）

**职责切分（原 `/security-review` 已并入本 skill，这段就是当时的分工结论）**：机器可判的部分交给 Qoder 内置 `security-scan` —— OWASP 逐项清单、密钥泄露扫描、依赖 CVE 审计由它承担（主会话用 `/security-scan` 触发，或让它扫指定路径）。**本轴只判扫描器判不了的差集**：这个改动在这个业务位置上的信任边界是否被绕过。审查前先跑内置扫描器拿到机器结论，本轴不重复列 OWASP 清单，只把它的结论按下面的严重度体系重新定级。

- SQL 注入、XSS、CSRF、路径遍历
- 硬编码密钥/密码/Token
- 输入未校验/未转义
- 权限检查缺失或不当
- 敏感信息泄露（日志中打印密码、错误信息暴露堆栈）
- 依赖版本是否存在已知漏洞

**三层边界防护**（逐层追问"这一层的最后一道防线究竟在哪"，任一层的防线依赖上一层 = 该层不合格）：

| 边界层 | 检查要点 |
|--------|---------|
| **入口边界** | 所有外部输入是否校验？认证是否完整？限流是否配置？ |
| **业务层** | 权限检查是否到位？事务边界是否正确？业务规则是否可被绕过？ |
| **数据层** | 查询是否参数化？敏感字段是否加密？备份是否安全？ |

#### 3.3 可维护性（Maintainability）

- 命名是否清晰、一致、可搜索
- 函数/方法是否过长（>50 行需拆分）
- 是否存在重复代码（DRY 原则）
- 注释是否必要且准确（不写"做了什么"的废话注释）
- 模块边界是否清晰（禁止跨层调用）
- 是否有"魔法数字"或硬编码常量

**Chesterton's Fence 原则**：看到不理解的代码，先理解它为什么存在，再决定是否删除或重构。不要盲目"简化"。

#### 3.4 性能（Performance）

- N+1 查询问题
- 循环内不必要的 IO/计算
- 大数据量场景未考虑分页/流式处理
- 缓存使用是否合理（缓存穿透/雪崩/一致性）
- 内存泄漏风险（未关闭的资源、无限增长的集合）
- 前端：不必要的重渲染、大列表未虚拟化

#### 3.5 可读性（Readability）

- 代码是否自解释（变量名/函数名即文档）
- 复杂逻辑是否有注释说明"为什么"
- 文件组织是否清晰（一个文件一个职责）
- import 是否整洁、无冗余
- 错误信息是否对开发者友好

### Step 4: 规格轴审查（Spec Axis）

**将代码实现与 Spec/PRD/ARCH 逐项对照：**

| 检查项 | 审查要点 |
|--------|---------|
| 需求覆盖 | 每个 User Story / 用例是否都有对应实现 |
| API 契约 | 接口签名是否与 SPEC-API-contract 一致（路径/方法/参数/响应） |
| 数据模型 | 实体/表结构是否与 SPEC-DDL 一致 |
| 错误码 | 错误码是否与 Spec 定义的错误码体系一致 |
| 状态流转 | 状态机是否与 PRD 中定义的状态流转一致 |
| 非功能需求 | 性能/安全/可用性指标是否有对应实现策略 |
| 安全需求逐条对齐 | PRD/ARCH 声明的安全需求（鉴权模型、数据分级、加密范围、审计留痕）是否**逐条**有实现与证据；缺项按 Major 起判，不得用"标准轴 3.2 安全性已合格"抵销——那是通量检查，这是与本项目需求清单的差集 |
| 分层合规 | 代码是否遵循 ARCH 中定义的分层依赖方向 |

> **实战经验**：标准轴合格但规格轴不合格的代码 = "写得好但做错了"。这是最危险的审查遗漏。

### Step 5: 问题分级与标注

使用统一的严重度标签体系：

| 严重度 | 含义 | 处理要求 | 典型示例 |
|--------|------|----------|---------|
| **Critical** | 阻断性 | 必须修复，不可合并 | 安全漏洞、数据丢失、崩溃、生产事故风险 |
| **Major** | 严重 | 应当修复，特殊情况需 Tech Lead 豁免 | 逻辑错误、性能隐患、Spec 偏离、缺少错误处理 |
| **Minor** | 一般 | 建议本次修复 | 命名不规范、缺少注释、代码重复 |
| **Nit** | 微小 | 可选修复，不阻塞合并 | 格式、空格、import 顺序 |
| **Optional** | 建议 | 建议后续迭代处理 | 架构优化、重构建议 |
| **FYI** | 信息 | 仅供知晓，无需行动 | 潜在的技术债务提醒、相关 ADR 引用 |

### Step 6: 输出结构化审查报告

**严格按以下格式输出，不要先夸再批。先列风险，再给建议。**

```markdown
## Code Review Report

**审查范围**: [PR/模块/提交]
**审查日期**: [YYYY-MM-DD]
**关联 Spec**: [Spec 文档路径，如无则标注"无关联 Spec"]
**结论**: [Approved / Request Changes / Rejected]

### 审查摘要
- 变更文件: N 个 (+X / -Y 行)
- 涉及模块: module-a, module-b
- Critical: N | Major: N | Minor: N | Nit: N | Optional: N | FYI: N

---

### Critical 问题（必须修复）

| # | 文件:行号 | 审查轴 | 问题描述 | 修复建议 |
|---|----------|--------|---------|---------|
| 1 | src/auth.ts:L42 | 标准轴-安全 | JWT 未校验过期时间 | 添加 exp 字段校验 |

### Major 问题（应当修复）
| # | 文件:行号 | 审查轴 | 问题描述 | 修复建议 |
|---|----------|--------|---------|---------|

### Minor 问题（建议修复）
| # | 文件:行号 | 审查轴 | 问题描述 | 修复建议 |
|---|----------|--------|---------|---------|

### Nit / Optional / FYI
| # | 文件:行号 | 严重度 | 问题描述 | 建议 |
|---|----------|--------|---------|------|

---

### 规格轴对齐检查
| Spec 条目 | 实现状态 | 备注 |
|-----------|---------|------|
| US-001 用户登录 | 已实现 | - |
| US-002 密码重置 | 未实现 | 缺少邮箱发送逻辑 |

### 亮点（值得肯定的设计）
- [具体描述，不要泛泛而谈]
```

### Step 7: 审查结论判定

| 条件 | 结论 |
|------|------|
| Critical = 0 且 Major = 0 | **Approved** |
| Critical = 0 且 Major <= 2（已确认修复计划） | **Approved with comments** |
| Critical > 0 或 Major > 2 | **Request Changes** |
| 规格轴严重偏离（核心 Spec 条目未实现） | **Rejected** |

### Step 8: 跟踪与闭环

- **Critical**：修复后必须重新审查
- **Major**：确认修复计划（本次修复或创建跟踪 Issue）
- **Minor/Nit**：记录为技术债务
- 所有 Critical/Major 关闭后方可 Approve

## 实战经验与常见陷阱

1. **变更过大（>500 行）时**：不要试图一次审完。要求拆分为多个小 PR，分批审查。大 PR 的审查质量会指数级下降。

2. **缺少上下文时**：暂停审查，要求补充需求说明。没有 Spec 的变更，先确认意图再审查实现。

3. **"看起来没问题"是最危险的结论**：每个审查必须至少覆盖标准轴 5 个维度中的 3 个 + 规格轴。

4. **审查意见有分歧时**：用代码/文档/规范说话，不用主观判断。如果规范没有覆盖，记录为规范待补充项。

5. **不要只挑毛病**：好的设计也值得记录和肯定。"亮点"章节不是客套，是正向强化。

## 失败处理

| 失败场景 | 处理方式 |
|----------|---------|
| 变更过大（>500 行） | 要求拆分，分批审查 |
| 无 Spec/需求文档 | 标注"无 Spec 对照"，仅做标准轴审查，建议补充 Spec |
| 审查意见分歧 | 引用规范/文档裁决，必要时引入第三方 |
| 修复引入新问题 | 重新执行完整审查 |
| 审查超时（>2 天） | 升级至 Tech Lead |
