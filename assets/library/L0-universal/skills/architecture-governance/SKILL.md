# 架构治理

## 核心理念

> **架构腐化不是突然发生的，是每次"就加一行"累积出来的。**
>
> 四个腐化信号：
> 1. 层次越来越多 — 改一个字段改 4-6 处文件
> 2. 对象越来越碎 — 8 种对象类型（VO/Form/DTO/BO/PO/DO/Query/Converter）
> 3. 继承越来越深 — 翻 3-4 层父类找一个方法
> 4. 注解越来越多 — 一行注解隐藏了不可见的副作用
>
> 来源：Matt Pocock improve-codebase-architecture + Harness 课程第 7 课 AI 架构治理。

## 与内置架构能力的分工（编排层）

本 skill 是**编排层**：证据背书的架构评审本身交给内置 `architecture-visualization:risk-quality-reviewer`（目录名 `risk-quality-reviewer`），本 skill 只做内置不做的那件事——**把腐化信号变成有阈值、有优先级、有节律的日常门禁**。

| 环节 | 交给内置（插件全名:目录名） | 本 skill 判什么 |
|------|--------------------------|----------------|
| 架构风险与质量评审（质量属性评估、技术债账、风险登记、fitness function、补救方案） | `architecture-visualization:risk-quality-reviewer` | 四个腐化信号的**阈值判定**：继承 >3 层、对象类型 >5 种、文件 >500 行、函数 >50 行 → P0/P1/P2 定级 + PASS/FAIL 二元结论（Step 2 的表只填这两件事） |
| 评审结论的呈现与再验证 | 同上（不重复生成第二份评审） | 处置节律：接触即迁移、新代码走新规范、每次变更而非季度大检查（Step 3 + 治理原则） |

🔴 **这些是内置能力，不要复刻**：不要在治理报告里重写一份质量属性/风险清单，也不要把内置已给出的评审结论按 Step 2 的表再排一遍。内置插件未安装时才走全量自查，并在报告头部标注"未用内置评审能力"。

## 触发条件

- 用户输入 `/architecture-governance`
- 用户输入 `/arch-check`（兼容别名：原独立命令已删除，语义并入本 skill）
- 定期架构健康度检查
- 代码审查中发现架构偏离
- 新模块开发前的架构合规预检

## 执行步骤

### Step 0: 确认检查范围（check-architecture 已并入本 skill）

- [ ] 全量检查（整个项目）
- [ ] 增量检查（本次变更）
- [ ] 特定模块检查

检查结论采用 **PASS / FAIL** 二元判定：存在 P0 问题 → FAIL；仅 P1/P2 → PASS（附问题清单）。

### Step 1: 扫描架构腐化信号

**1.1 分层依赖检查**
```bash
# 检查是否存在反向依赖（下层依赖上层）
# Controller 层不应被 Service 层直接 import
# Service 层不应被 Repository 层依赖
```

**1.2 对象体系检查**
```bash
# 统计对象类型数量
# 理想: Entity + Request + VO (3种)
# 警告: >5 种对象类型 = 过度碎片化
```

**1.3 继承深度检查**
```bash
# 检查继承链深度
# 警告: 继承深度 > 3 层
# 建议: 用组合替代继承
```

**1.4 文件大小检查**
```bash
# 找出超过 500 行的文件
# 找出超过 50 行的函数
```

### Step 2: 输出治理报告

```markdown
## Architecture Governance Report

**检查日期**: <YYYY-MM-DD>
**检查范围**: <模块/全项目>
**检查结论**: PASS / FAIL

### 架构健康度评分: [A 至 F 五档]

### P0 问题（必须立即修复）
| # | 问题 | 位置 | 影响 | 建议修复方案 |
|---|------|------|------|-------------|
| 1 | <问题> | <文件:行号> | <影响> | <方案> |

### P1 问题（本迭代内修复）
| # | 问题 | 位置 | 影响 | 建议修复方案 |
|---|------|------|------|-------------|

### P2 问题（纳入技术债务）
| # | 问题 | 位置 | 影响 | 建议修复方案 |
|---|------|------|------|-------------|

### 架构指标
| 指标 | 当前值 | 目标值 | 状态 |
|------|--------|--------|------|
| 最大继承深度 | | <=3 | ✅/❌ |
| 对象类型数 | | <=5 | ✅/❌ |
| 最大文件行数 | | <=500 | ✅/❌ |
| 最大函数行数 | | <=50 | ✅/❌ |
| 分层违规数 | | 0 | ✅/❌ |
```

### Step 3: 建议重构方案

对每个问题给出具体的重构方案：
- 重构步骤（小步迭代）
- 风险评估
- 验证方式

## 治理原则

1. **治理不是一次性大扫除** — 是可持续的增量改进
2. **接触即迁移** — 老代码不改的不动，碰到了就顺手迁移
3. **新代码走新规范** — Rule 自动生效，不再引入新的架构问题
4. **每次变更检查** — 架构治理融入日常开发，不是季度大检查
