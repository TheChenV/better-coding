# 测试计划、用例构造与执行报告

## 产出契约（环节卡为单一契约源）

| 项 | 契约 |
|----|------|
| 产出物 | 测试用例与脚本（Step 1a）+ 测试执行结果 + `docs/test/spec-{业务}-测试报告.md`（覆盖率、关键路径通过率、失败用例根因） |
| 模板依赖 | 无（测试计划以 `docs/spec/` 下 SPEC-TEST 为依据；测试命令取 AGENTS.md 测试说明段 / `.qoder/techstack-commands.json`） |
| 归档位置 | `docs/test/`（阶段 A 不预建该目录，v9.4.0 S7 起首写时自建；`不假定阶段 A 已建`） |
| 产出自检 | 三类用例逐类齐备且声明的异常类型逐一对应到用例；SPEC-TEST 用例全执行且关键路径达标；对外 API 契约测试覆盖；失败用例有根因（禁跳过删除）；覆盖率达标并说明未覆盖关键路径；无 Flaky（重复 3 次一致） |
| 收尾 | 3 步同步 |

## 触发条件

- 用户输入 `/run-tests` 命令
- 用户输入 `/run-test`（兼容别名：原独立命令已删除，语义并入本 skill）
- 用户输入 `/create-test`（兼容别名：原独立 skill 已删除，用例构造判据并入本 skill Step 1a）
- 新功能实现后需要补充测试用例；修复 Bug 后需要添加回归测试
- 测试覆盖率不达标需要补充，或用户要求为特定方法/模块生成测试
- 功能实现完毕后需要验证测试
- 提交前回归测试 / 代码审查前确认测试通过
- CI/CD 流水线中的测试阶段

## 核心原则

> **v8.4.0 入参优先与对外表述**：骨架 7·2 提示词已内联三位评审（代码质量 / 安全 / 测试与运维）各自关注点，用户显式给出角色清单时**以提示词为准**；报告与结论一律用“可以上线 / 不建议上线、必修项、已接受的风险、回滚方案”这类用户语言，`Ship Decision`/`persona`/`fan-out`/`Must Fix` 等内部名不得写进用户可见提示词。

> **测试必须可重复执行、可独立运行、可快速反馈。** 测试执行后必须输出结构化报告，失败用例必须分析根因。

## 执行步骤

### Step 1: 确认测试范围

明确本次测试的范围：

- [ ] 全量测试（所有测试用例）
- [ ] 增量测试（仅本次变更相关）
- [ ] 特定模块测试
- [ ] 集成测试
- [ ] 契约测试

### Step 1a: 用例构造（原 `/create-test` 全量并入）

> **用例不是"能跑就行"，而是三类各就各位**：正向证明能用、异常证明拒得干净、边界证明不塌。
> 缺任一类，覆盖率数字照样好看，但闸门拦不住下一次回归。

**1) 先读被测定义**（下表缺任一项 = 信息不足，不得开始写用例）：

| 项 | 要确认什么 |
|----|-----------|
| 签名 | 参数类型与返回类型、必填与可选 |
| 归属 | 所属类/模块及其职责 |
| 依赖 | 其他服务/组件（这一项决定 Mock 面） |
| 异常 | 可能抛出的错误类型与各自的触发条件 |
| 前后置 | 前置条件与可断言的后置状态 |

**2) 数据依赖与 Mock 策略**：参数有效域与参数间约束（含 null / 空值 / 极大值三类特殊值）；外部依赖逐项判定 Mock 还是真连（DB 表记录、外部接口、测试文件、环境变量）；**Mock 只隔离边界**（外部依赖），不得 Mock 被测逻辑本身——把被测方法自己替身掉等于零断言。

**3) 测试数据工厂**：用 Builder / Factory 函数构造数据，数据自描述（看数据即知意图），避免魔法数字（改命名常量）；用覆盖式参数（`overrides`）而非复制整份字面量。构造成本过高时引入 Fixture 文件，不要就地手搓。

**4) 三类用例逐类补齐**：

| 类别 | 最低要求 |
|------|---------|
| 正向（Happy Path） | 主业务路径各 ≥1 条 + 组合场景（多参数交互，如多商品合计）≥1 条 |
| 异常（Error Path） | 第 1) 步表里**每个**声明的异常类型都有对应用例，且断言副作用真的发生（如支付失败要断订单已回滚） |
| 边界（Boundary） | 每个数值/长度约束取下界、上界、刚越界三点（如上限 999 → 999 通过、1000 拒绝）；空集合与单元素；并发与幂等（同请求重复提交不得产生重复副作用） |

**5) 门槛与豁免**：所有新增业务逻辑方法必须有用例；修复 Bug 必须先写一条**先失败后通过**的回归用例（在修复前跑一次确认它真的红）；核心业务路径（支付、认证）要求 100% 覆盖；模块覆盖率低于基线（通常 80%）需补齐，判定见 Step 3。确实不可测的代码（纯配置、生成代码）标注豁免并写明理由，禁止静默跳过或删除用例。

### Step 2: 执行测试

```bash
# 按项目技术栈执行（以下命令需根据项目实际配置）
# 【__已预填：测试命令，请核对__】
# 例如：
# - Node.js/Jest: npm test
# - Java/JUnit: mvn test
# - Go: go test ./...
# - Python/pytest: pytest

# 如需覆盖率报告：
# 【__已预填：覆盖率命令，请核对__】
# 例如：
# - Node.js: npm test -- --coverage
# - Java: mvn test jacoco:report
# - Go: go test -coverprofile=coverage.out ./...
# - Python: pytest --cov=src --cov-report=term-missing
```

### Step 3: 分析测试结果

**通过标准**：
- [ ] 所有测试用例通过（0 failures）
- [ ] 覆盖率不低于项目基线（通常 ≥80%）
- [ ] 无跳过的测试（除非有明确理由并标注）

**失败处理**：
- 分析失败原因：是新代码引入还是环境问题
- 区分 Flaky Test（不稳定测试）和真实失败
- 对于真实失败，定位根因并修复

## 失败处理

| 失败场景 | 处理方式 |
|----------|----------|
| 测试失败（新引入） | 修复代码或测试，重新验证 |
| 测试失败（已有 flaky test） | 记录为已知问题，创建 Issue 跟踪；时序/随机因素导致的偶发失败改确定性数据 |
| 覆盖率不达标 | 按 Step 1a 补边界/异常用例（不是补断言数量） |
| 代码不可测试（强耦合） | 先重构引入依赖注入，再编写测试 |
| 外部依赖无法 Mock | 使用集成测试替代，或引入 Adapter 层隔离 |
| 环境无法运行测试 | 至少确保编译通过，标注"测试待 CI 验证" |
| 覆盖率始终无法达标 | 评估是否为不可测代码（纯配置/生成代码），标注豁免并写明理由 |
