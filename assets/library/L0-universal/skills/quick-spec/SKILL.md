# 小改动轻量 Spec 快速通道

## 核心理念

> **规范的重量应与变更的重量匹配。**
> 小改动走全流程 SDD 是"瀑布化"的根源；但完全不写 spec 又退回 Vibe Coding。
> 快速通道 = 一页纸 spec：方案、范围、风险、验收标准四段，绝不提前写实现代码。
> 判定标准：通读这份规划后，"普通应届生一个月内可完成"即算达标。

## 触发条件

- 用户输入 `/quick-spec`
- 变更满足快速通道准入条件（见下）
- 用户明确说"小改动，走快速通道"

## 准入条件（全部满足才可用）

- [ ] 预计修改文件 ≤ 5 个
- [ ] 不涉及数据库 Schema 变更（或仅加列）
- [ ] 不涉及新增外部依赖/第三方服务
- [ ] 不涉及架构分层变化
- [ ] 不涉及认证/支付/个人数据等安全敏感域

任一不满足 → 退出快速通道，建议走 /create-proposal 标准流程。

## 执行步骤

### Step 1: 快速对齐（最多 2 轮追问）

- 变更目标与验收标准
- 影响面确认（哪些文件/接口/页面）

### Step 2: 产出单页快速 Spec

**产出路径**: `docs/spec/QUICK-{slug}.md`

```markdown
# 快速 Spec: {变更标题}

> 通道: quick-spec ｜ 日期: {YYYY-MM-DD} ｜ 状态: Approved / Pending

## 1. 方案（怎么做，一段话）
{不写实现代码，只写到"改哪个文件、用什么方式"的粒度}

## 2. 范围（做什么 / 不做什么）
- 做: {清单}
- 不做: {显式排除}

## 3. 风险
| 风险 | 缓解 |
|------|------|

## 4. 验收标准（可机器验证）
- [ ] {条件 1，如"运行 npm test 全部通过"}
- [ ] {条件 2，如"GET /api/x 返回 200 且含字段 y"}
```

### Step 3: 用户确认

- 用户 Approve 后进入实现（可直接编码或交给 /implement-feature 简化模式）
- 实现阶段遵守该 spec：超出范围的改动须先回到本 spec 追加

### Step 4: 收尾

- 验收标准逐条验证（verification-before-completion，Qoder 内置）
- 执行 harness-continuous-sync 同步（QUICK spec 登记进 profile.knownDocs）

## 输出物

- docs/spec/QUICK-{slug}.md（单页 spec）
- 验收验证证据

## 失败处理

| 失败场景 | 处理方式 |
|----------|----------|
| 准入条件不满足 | 退出快速通道，转 /create-proposal |
| 实现中发现范围扩大（>5 文件） | 暂停，升级通道：QUICK spec 转正式 SPEC 流程 |
| 验收标准无法机器验证 | 重写验收标准为可执行条件，禁止"看起来正常"式标准 |
