# 模块联调编排（环节 6）

## 核心理念

> **联调 = 可回退 + 一次一改 + 契约测试全通过才算完。**
> 围绕主模块 A 的跨模块集成调试：启动 A 及其依赖模块的服务，每模块分配一个专家（并行 sub-agent），把 A 中的 Mock/Stub 调用逐个替换为真实调用，通过契约测试验证集成正确性。
> 三条铁律：**先建 Git 检查点再动手**；**一次只改一个调用**（批量改 Mock 无法隔离失败源）；**优先改 A 适配依赖，不改依赖接口**（依赖被多方消费，改接口即破坏他人契约）。

## 产出契约（强制，环节卡为单一契约源）

| 项 | 契约 |
|----|------|
| 产出物 | 集成报告（固定 Markdown 模板，见 Step 8）+ 契约测试 100% 通过的代码变更 |
| 归档位置 | `docs/spec/联调记录-{日期}.md` |
| 前置产物 | SPEC-BE（API 契约/OpenAPI）、各模块契约测试、可启动的模块代码（环节 5 产出） |
| 产出自检 | Git 检查点已记录 stash hash；所有服务健康检查通过；Mock→真实一次一改；契约测试 Total=Passed；报告 4 段完整（启动状态/变更清单/测试结果/遗留问题） |

## 执行步骤

### 根因回灌（v9.0.0，§5.3）

联调暴露的接口与契约问题，收尾时必须回写为开发环节的阈值门禁条目（`references/sdd-gates-checklist.md`
或 `implement-feature` 的前置检查），不得只留在联调报告里——报告没人回看，门禁才会被真的执行。
（7 Phase）

> **v8.4.0 对外表述与入参优先**：面向用户与提示词手册一律称「第 1 步 … 第 7 步」，Phase 编号仅本 skill 内部使用，不得进入用户可见提示词（Check 7f 拦 `Phase0-6`、`Red Flag`、`meet skill` 等内部名）；联调方式 A/B、主模块与模块清单、契约清单路径**以提示词显式给出者为准**。

### Step 1 (Phase 0): 创建 Git 检查点

任何操作开始前，确保所有变更可回退：

```bash
git add -A
git stash
```

记录当前 stash hash，供后续恢复。**跳过本步直接改代码是 Red Flag。**

### Step 2 (Phase 1): 识别模块范围

1. 识别主模块 A
2. 分析 A 的依赖，列出所有需启动的依赖模块
3. 为每个模块确定：代码目录路径 / 启动命令 / 端口号 / 契约测试执行命令

产出模块范围表（含契约表，作为 Mock→Real 切换清单基准）。

### Step 3 (Phase 2): 服务启动

对每个模块（A + 依赖）：

1. **检查服务是否已运行**：检查端口占用；若占用，判断是否本会话启动
2. **非本会话启动的服务不得重启**（会中断其他使用者）→ 另起端口启动新实例
3. **启动服务**：执行启动命令 → 等待健康检查通过 → 记录服务地址与端口

**服务未就绪就开始改代码是 Red Flag；多模块抢同端口是 Red Flag。**

### Step 4 (Phase 3): 并行专家分配

使用 Agent tool 并行启动 sub-agent，每模块分配一个专家。**所有 Agent 调用必须在同一轮次发出，确保真并行。**

每个模块专家的职责：

```
1. 读取当前模块的代码与配置
2. 确保模块服务正常运行
3. 若需修改代码以支持模块 A 的真实调用 → 执行修改
4. 约束：所有变更必须向前兼容（不得破坏现有接口契约）
5. 输出：变更清单 + 当前模块状态报告
```

**sub-agent 模型约束**：
- sub-agent 不能再嵌套 spawn sub-agent——禁止一个专家委托另一个专家
- 每个 sub-agent 有独立上下文窗口，只向主会话返回报告
- 专家间需要沟通时，由主会话汇总协调（或多专家会议机制），禁止相互依赖等待

### Step 5 (Phase 4): Mock→真实调用转换

所有专家报告返回后：

1. 整合各模块专家报告
2. 修改模块 A 代码：将 Mock/Stub 调用替换为对依赖模块的真实调用
3. 调用地址与端口指向 Step 3 启动的服务
4. 遵循增量修改原则：**一次只改一个调用**，改完即验证（禁批量替换——无法隔离失败源）
5. 处理专家发现的兼容性问题（如接口签名不匹配）

> Mock 开关机制见本文《Mock 开关约定》一节；敏感值（地址/密钥）一律环境变量。

### Step 6 (Phase 5): 契约测试循环

1. 运行模块 A 的**全部**契约测试
2. 若失败：分析原因 → 识别需修改的模块与代码 → 按向前兼容原则修复 → 重跑契约测试
3. **循环直至 100% 通过**
4. 重要原则：
   - **优先改 A 适配依赖，避免修改依赖模块接口**
   - 依赖模块变更不可避免时，必须保证向前兼容
   - 每次变更后跑全量契约测试（禁止累积变更后一次性测试）

> 联调期间不改接口契约；契约本身有误则回环节 3 走 `/spec-delta`。

### Step 6a: 契约测试判据（原 `/contract-test` 全量并入）

> **契约是服务间的法律合同**：提供方不可单方面破坏契约，消费方不可依赖契约外的行为。
> Step 6 的循环跑的就是这套判据；环节 5 产出契约测试用例时同样按本节出题。只验契约一致性（不做跨模块联调）时可单跑本节，跳过第 1-5 步。

**基准（唯一契约源）**：以 SPEC-BE / OpenAPI 为准（`openapi.yaml|openapi.json|contracts/*.yaml`）；逐端点确认路径与 HTTP 方法、参数位置（Path/Query/Header/Body）、响应状态码与 Body Schema、认证方式、错误响应格式。契约缺失或过期时，先从代码提取实际接口、生成契约后再测——不得对着空气写断言。

**五组断言**（逐端点补齐；缺任一组 = 契约测试留了口子）：

| 组 | 判什么 | 典型漏网 |
|----|--------|---------|
| 正向请求 | 符合契约的请求返回声明的状态码，Body 字段与类型逐一对 | 只断 201 不断字段类型 |
| 严格模式 | 响应**不含契约外字段**（`Object.keys` 逐一对齐 allowed 集合） | 多返回一个内部 ID 无人报 |
| 状态码矩阵 | 成功/参数错/未认证/不存在分别 201/400/401/404；500 不泄露内部信息（无 `stack`、无内部结构） | 参数错回 500；500 直接回堆栈 |
| 违反契约的请求 | 缺必填、类型错、无认证三类各自回 400/401 | 缺字段时静默取默认值后 200 |
| 错误结构一致 | 所有错误响应的键集合相同（全局一致），且 `message` 指出出错字段 | 400 有 `code`、401 没有 |

**报告与处置**：逐端点列 正向/格式/状态码/错误处理 四列结论 + 违反项表（接口 / 问题 / 严重度 / 建议）。违反项的处置：修复代码，或更新契约——**更新契约需提供方与消费方双方同意**；破坏向后兼容的变更必须走版本升级（v1→v2），不得原地改接口，且要通知所有消费方。契约版本冲突时以 Git 中最新合入的版本为准。测试环境不可用时用 Mock Server（如 Prism）基于契约文件模拟，不得跳过契约验证。

## Mock 开关约定（原 L0 规则 `mock-switch-convention`，v8.5.0 下沉至本 skill）

> 本条只在环节 6 联调用，故不再是常驻规则；正文由本 skill 承载，提示词手册【环节6】各步骤（`/integrate-modules` 引擎）指回这里。
> Mock 开关是开发/联调两阶段平滑切换的基础设施：没有开关，联调就要改代码；改代码，就破坏了"一次一改、可回退"的联调纪律。

1. **外部接口必须有 Mock 开关** — 依赖第三方 API / 其他团队服务时，必须提供开关机制：开发阶段开 Mock 用本地模拟数据自测，联调阶段关 Mock 调真实接口做集成验证。
2. **远端中间件必须有 Mock 开关** — 消息队列、缓存、数据库等同理：开发阶段用内存队列/本地缓存/嵌入式数据库自测，联调阶段连真实服务。
3. **敏感值一律环境变量** — 服务地址、端口、密钥、Token 一律通过环境变量注入（如 `MOCK_ENABLED=false`），禁止硬编码进源码，禁止提交仓库。
4. **开关粒度到依赖项** — 每个外部依赖可独立切换，不做全局一刀切；联调时"一次只改一个调用"（见上文 Step 5）。
5. **Mock 数据脱敏** — 样本数据必须脱敏，覆盖正常 + 异常场景（错误码、超时、空数据），与 API 契约（SPEC-BE/OpenAPI）保持一致。

### 阶段切换

| 阶段 | Mock 开关 | 验证方式 | 对应环节 |
|------|----------|---------|---------|
| 开发（模块内自测） | 开启（本地模拟数据/本地中间件实现） | 单元测试 + 契约测试（Mock 侧） | 环节 5 |
| 联调（跨模块集成） | 逐个关闭（一次一个依赖，Mock→真实） | 契约测试循环至 100% 通过 | 环节 6（本 skill） |
| 集成测试 | 全部关闭（真实链路） | API + E2E 测试 | 环节 7 |

**切换纪律**：
- Mock→真实的切换只通过开关（环境变量/配置）完成，**禁止以删除 Mock 代码的方式切换**（Mock 实现保留，供回归与离线开发复用）
- 联调阶段发现接口不匹配：优先改调用方适配依赖，不改依赖接口；契约本身有误回环节 3 走 `/spec-delta`
- 服务启动脚本（如 `init.sh`）须打印当前运行模式（Mock 模式 / 真实模式），便于确认开关状态

**禁止**：硬编码外部服务地址/密钥/Token · 无 Mock 开关直连外部服务开发 · 一次性批量切换所有 Mock · 以删除 Mock 代码代替关闭开关 · Mock 数据与 API 契约脱节。

## Red Flags（出现任一立即纠正）

- 🚩 跳过 Git 检查点直接修改代码
- 🚩 多模块启动在同一端口，造成冲突
- 🚩 sub-agent 相互依赖、互相等待
- 🚩 修改依赖模块的非兼容接口
- 🚩 批量替换 Mock 调用（应一次一改）
- 🚩 跳过每次变更验证、累积变更后统一测试
- 🚩 服务未就绪就开始改代码

## 常见错误信念

| 错误信念 | 现实 |
|---------|------|
| "直接重启同端口服务即可" | 外部启动的服务重启会中断他人，必须另起端口 |
| "改一下依赖模块接口没关系" | 依赖被多方消费，改接口即破坏其他消费者，必须向前兼容 |
| "一次把所有 Mock 全换掉" | 多处同时变更无法隔离失败源，一次改一个 |
| "先改完代码再统一测试" | 问题会累积，改一个测一次才能定位 |

## 失败处理

| 失败场景 | 处理方式 |
|----------|----------|
| 契约测试反复失败无法收敛 | 检查契约本身是否有误——有误回环节 3 `/spec-delta`，无误则缩小范围逐个调用隔离 |
| 依赖模块专家报告接口不匹配 | 优先改 A 适配；确需改依赖时确保向前兼容并通知所有消费方 |
| 端口冲突且无法另起端口 | 停止联调，与用户确认外部服务处置方案，禁止擅自杀掉非本会话进程 |
| 联调引入回归 | `git stash pop` 回到检查点，重新分析后小步重入 |
| 破坏性操作（合并/重置/删分支） | 先出操作清单，经用户二次确认后执行 |
