# 代码简化

## 核心理念

> **Chesterton's Fence（切斯特顿栅栏）：在你理解一个栅栏为什么存在之前，不要拆除它。**
>
> 代码简化不是"看到复杂就删"，而是先理解为什么存在，再决定是否简化。
> 清晰胜过聪明。500 行以上的文件必须拆分。
>
> 来源：Addy Osmani agent-skills code-simplification — 先理解再删，清晰胜过聪明。

## 触发条件

- 用户输入 `/code-simplification`
- 代码审查中发现复杂度高的模块
- 定期代码健康度治理

## 执行步骤

### Step 1: 识别简化目标

```bash
# 找出大文件
find . -name "*.ts" -o -name "*.py" -o -name "*.java" | xargs wc -l | sort -rn | head -20

# 找出深层嵌套
grep -rn "if.*if.*if" --include="*.ts" --include="*.py" --include="*.java"

# 找出重复代码模式
# 按项目技术栈使用对应工具
```

### Step 2: Chesterton's Fence 检查

> **在修改任何代码之前，先理解它为什么是这样。**

对每个待简化的代码段问：
1. 这段代码解决什么问题？
2. 为什么用这种方式解决？（历史原因？技术约束？）
3. 如果删除/简化，会破坏什么？
4. 有没有测试覆盖这段代码？

**如果无法回答以上问题，不要动这段代码。**

### Step 3: 应用简化策略

| 策略 | 适用场景 | 操作 |
|------|---------|------|
| **提前返回** | 深层嵌套（>3 层 if-else） | 用 guard clause 替代嵌套 |
| **提取函数** | 函数超过 50 行 | 按职责拆分为多个小函数 |
| **删除死代码** | 注释掉的代码、未使用的导入 | 直接删除（Git 有历史） |
| **合并重复** | 多处相同逻辑 | 提取为公共函数/组件 |
| **简化条件** | 复杂的布尔表达式 | 用命名变量/函数表达意图 |
| **替换魔法数字** | 硬编码的常量 | 提取为命名常量 |

### Step 4: 验证

- [ ] 编译通过
- [ ] 全量测试通过
- [ ] 代码行数减少（或不变但可读性提升）
- [ ] 圈复杂度降低

## 反模式（绝对禁止）

1. **不理解就删除** — 注释掉的代码可能是临时 workaround，删除前确认
2. **过度抽象** — 为了"优雅"把简单逻辑封装成复杂框架
3. **一次性大重构** — 简化应该是小步迭代，不是一次性大扫除
