# 架构决策记录

## 触发条件

- 用户输入 `/create-adr`（或说"写个 ADR/记录架构决策"）
- 做出影响系统架构的技术决策时
- 技术选型需要正式记录时
- 架构评审中产生的决策需要归档
- 需要回溯"为什么当初这样设计"时

## 核心原则

> **ADR 是不可变的。** 一旦记录，只能被新的 ADR 取代（Superseded），不可修改或删除。这确保了决策历史的完整可追溯。

## 执行步骤

### Step 1: 明确决策点

清晰定义需要做出的决策：

**必须回答：**
- **决策标题**：一句话概括（如"选择 PostgreSQL 作为主数据库"）
- **决策背景**：为什么现在需要做这个决策？
- **驱动因素**：哪些需求/约束驱动了这个决策？
- **决策范围**：影响哪些系统/模块/团队？

**格式：**
```
决策点: <标题>
背景: <为什么需要做这个决策>
驱动因素:
  - <因素1: 如性能要求>
  - <因素2: 如团队技能>
  - <因素3: 如成本约束>
影响范围: <涉及的系统/模块>
```

### Step 2: 列出替代方案（≥2个）

列出所有可行的替代方案：

**要求：**
- 至少 2 个方案（含"不做任何改变"选项）
- 每个方案需有足够细节以供评估
- 包含方案的优缺点分析

**方案描述模板：**
```markdown
### 方案 A: <名称>
- 描述: <2-3句话说明方案内容>
- 优点:
  - <优点1>
  - <优点2>
- 缺点:
  - <缺点1>
  - <缺点2>
- 风险: <主要风险>
- 成本: <实施/运维成本估算>
```

### Step 3: 量化对比

使用统一的评估维度进行对比：

```markdown
| 评估维度 | 权重 | 方案A | 方案B | 方案C |
|----------|------|-------|-------|-------|
| 性能满足度 | 30% | 9/10 | 7/10 | 8/10 |
| 开发效率 | 25% | 7/10 | 9/10 | 8/10 |
| 运维成本 | 20% | 6/10 | 8/10 | 9/10 |
| 团队熟悉度 | 15% | 8/10 | 5/10 | 7/10 |
| 扩展性 | 10% | 9/10 | 7/10 | 6/10 |
| **加权总分** | 100% | **7.9** | **7.4** | **7.8** |
```

**评估原则：**
- 权重由项目实际需求决定
- 打分基于事实和数据（PoC结果、Benchmark）
- 避免主观偏好影响
- 团队投票可作为参考但非决定因素

### Step 4: 记录决策与后果

编写正式的 ADR 文档：

**文件命名：** `docs/arch/adr/ADR-<NNN>-<title>.md`

**ADR 模板：**
```markdown
# ADR-001: <决策标题>

## 状态
Accepted | Proposed | Deprecated | Superseded by ADR-XXX

## 日期
YYYY-MM-DD

## 背景
<描述驱动这个决策的上下文和原因>

## 决策
<明确说明做出的决策，使用主动语态>
我们决定采用 <方案X>，因为 <核心理由>。

## 替代方案
### 方案A: <名称>
<简述及放弃原因>
### 方案B: <名称>
<简述及放弃原因>

## 后果

### 正面后果
- <好处1>
- <好处2>

### 负面后果
- <代价1>
- <代价2>

### 需要注意
- <后续需要关注的事项>

## 相关决策
- 关联 ADR: <如有>
- 关联需求: <Issue/PRD链接>
```

### Step 5: 不可变归档

**归档规则：**
- ADR 文件一旦状态变为 `Accepted`，内容不可修改
- 需要变更时，创建新 ADR 并将旧 ADR 标记为 `Superseded by ADR-XXX`
- 所有 ADR 按序号递增，不可跳号
- 在项目中维护 ADR 索引（`docs/arch/adr/README.md`）

**索引模板：**
```markdown
# Architecture Decision Records

| # | 标题 | 状态 | 日期 |
|---|------|------|------|
| 001 | 选择PostgreSQL | Accepted | 2024-01-15 |
| 002 | 采用微服务架构 | Accepted | 2024-01-16 |
| 003 | 替换为MongoDB | Superseded by 007 | 2024-02-01 |
```

**Git 提交规范：**
```bash
git add docs/arch/adr/
git commit -m "docs(adr): add ADR-001 choose PostgreSQL as primary database"
```

### Step 6: 追加 harness-continuous-sync 同步步骤

**执行 harness-continuous-sync 步骤 1-3**（唯一规范：.qoder/commands/live-refresh.md）。

## 输出物

- 格式规范的 ADR 文档
- 量化对比分析表
- ADR 索引更新
- Git 提交记录

## 适用条件

- 影响系统整体架构的决策
- 技术栈/框架/中间件选型
- 数据模型/存储方案选择
- 通信协议/API 风格决定
- 部署/运维方案选择
- 任何"以后可能会问为什么"的决策

## 失败处理

| 失败场景 | 处理方式 |
|----------|----------|
| 无法达成共识 | 由架构师/技术负责人做最终决定，记录不同意见 |
| 决策依据不充分 | 安排 PoC/调研，补充数据后再记录 |
| 决策被证明错误 | 创建新 ADR 取代旧决策，旧 ADR 标记 Superseded |
| 遗漏了重要方案 | 补充新 ADR，在相关决策中引用 |
| ADR 编号冲突 | 以 Git 提交顺序为准，后提交者重新编号 |
