# UI 设计编排（SDD 环节 4 / Phase 4）

## 核心理念

> **UI 设计环节 = SPEC-UI 规范产出 + 内置设计能力编排 + 还原核对基准（G2/G3）。**
> 本 skill 不复制 Qoder 内置的设计类 skill（ui-designer、ui-ux-pro-max-design、design-qa、design-system-capture、accessibility-review、responsive-design 等），只做三件事：
> 1. **Step0 前置确认**：确认「带界面应用」与「环节 1·3 交互原型工程已就位」两件事，再进入单路线执行；设计执行的路由目标一律是**已存在的内置 skill**，不新建重复子 skill（"编排不复制"纪律）；
> 2. 按 SPEC-UI 模板产出设计规范（设计 Token/排版/四态/组件/响应式/A11Y）；
> 3. 编排调用内置设计能力完成实现与审查，内置能力缺失时降级为纯文档流程。

### 保真度分层（Phase1 原型 vs Phase4 设计）

| 阶段 | 产物 | 保真度 | 关注点 |
|------|------|--------|--------|
| 环节 1·步骤 3（Phase1） | `docs/prd/PRD-{应用}-交互原型/`（可运行工程） | 低-中保真 | 页面结构、功能流转、用户操作逻辑；**不定稿**色彩/品牌/精确色阶，但仍须成体系：真 SVG 图标、字阶/间距/圆角/海拔各有阶、正文有行长上限、主-次按钮有层级 |
| 环节 4（Phase4，本 skill） | SPEC-UI + `references/ui/` 设计工程（阶段 A 不预建该目录，v9.4.0 S7 起首写时自建；`不假定阶段 A 已建`） | 高保真 | 视觉风格、品牌一致性、像素级细节；完整配色/精确字阶/最终素材/精细动效 |

分两步而非一步直出高保真的理由（AINative 4.1）：交互与视觉的输入/输出/评判标准不同，合并导致 Prompt 过复杂、质量下降；先原型定流程再基于原型迭代视觉，避免评审变动引发设计返工；视觉与交互解绑后，后端不必等高保真稿即可确认页面字段，解锁并行。

> 🔴 **v9.11.0 界定：「低保真」指的是视觉决策尚未定稿，不是可以不好看。**
> 旧行「色彩粗粒度、图标占位、不涉品牌色」里的**「图标占位」已被实测执行成 Unicode 字形顶替**（真环境一个 `<svg>` 都没有，
> 回收站用 `␡` 结果渲染成英文字面「DEL」），「色彩粗粒度」被执行成一个字号一套圆角。属主据此两度判不合格，
> 而当时全部判据绿灯。占位的意思从来是"色值后面还会改"，不是"这里可以不放真图标"——
> **字符图标、无字阶、无间距阶属未完成，不属低保真**；判据见步骤 P3 六条底线。

### 环节衔接

- **上游（环节 1·步骤 3）**：`/create-proposal` 步骤 3 触发 `ui-design` skill，产出并冻结交互原型工程——本环节的视觉深化基准。
- **下游（环节 5 前端开发）**：本环节产出 `references/ui/` + SPEC-UI 是环节 5 FE「加载设计系统」子阶段的输入（SPEC-UI 存在 → 规范驱动加载 design tokens；SPEC-UI 缺失 → 先回 4·1 补规范，不带未定稿的规范进实现）。
- **跳过**：Backend-Only 应用本环节整体跳过（进展图标 ⊘），环节 5 直接走后端路径。

## 交互原型工程（v9.0.0 自 ui-design 并入，环节 1·3 执行引擎）

并入不是把两份文档拼起来：原型阶段与设计阶段共用同一套页面清单与同一个落盘契约，
拆成两个 skill 就会出现两份「页面数 = PRD 第 4 章」的验收线与两处落盘路径口径。

### 步骤 P1：读 PRD 第 4 章，建页面清单与跳转图
- 页面数与 PRD 第 4 章严格 1:1；每页标注关键交互与异常分支
- 无法确定的页面先用选择卡问，不自己补页面

### 步骤 P2：搭工程骨架（全部假数据）
- 目录 `docs/prd/PRD-{应用}-交互原型/`：源码 + 依赖清单 + 启动方式说明
- Mock 数据覆盖正常/异常/边界三类；不接真实后端接口；敏感值一律走环境变量
- 原型与生产工程严格分离（原型不得被当成生产代码继续长）
- 骨架不由 AI 现写：走库根 `assets/templates/numbered-workflows/`（项目级安装 = `.qoder/skills/better-coding/assets/templates/numbered-workflows/`）
  的七步编号工作流，原型数据取 `plans/prototype.json`，落盘件在项目侧 `.scaffold/step<编号>.mjs`：
  **段 A 理解目标** 读 `workflows/<编号>/workflow.md` → **段 B 拼脚本**
  `node <库根>/assets/templates/numbered-workflows/numbered-workflow.mjs compose --stack prototype --vars <values.json> --workflow <编号> --project <项目根>`
  → **段 C 执行** 跑落盘件 → **段 D 验证** 按退出码判定；失败即问用户「重试还是跳过」，
  不自行继续。禁止修改用户已有 .qoder/（引擎按路径段拦，命中即退出码 2）。
  原型至少跑到 04-verify-paths；预览.html 的契约校验见下方同名小节，不在此重复。

### 步骤 P2.5：定投入度 + 取设计基调（v9.11.0 新增，不可跳）

原型阶段不定稿视觉，但**必须先有一个成体系的基调**再开始画页面，否则 18 页会画成 18 个样子。

**0) 先定两维度投入度**（不是二选一：底座恒开，第二维度按品类调档）

| 品类信号 | 体系底座（`ui-ux-pro-max`） | 独一性与文案 |
|---|---|---|
| 后台/管理页、表单密集、仪表盘、编辑器、数据报告 | 全开（必做） | **仍要做**，但收敛在"一个字族性格 + 一处记忆点"——把大胆只花在一个地方，周围保持安静纪律 |
| 品牌官网、营销落地页、portfolio、需要"让人眼前一亮" | 全开 | 全开，走两遍法（先出计划→对着简报自检是否通稿→再写码） |
| 信号混合 / 材料里读不出品类 | — | **发一张选择卡问属主**，两档各写清代价 |

- 🔴 **不设默认值**：判不出又不问、自行归"工具类所以少做独一性"，违反「探测 ≠ 决策」。
  实测理由：本库检索给 notebase（笔记工具类）的推荐是「奶油底 `#FFFBEB` + 琥珀 `#D97706` + 暖灰」，
  而这正是"AI 生成页默认特征"清单点名的第一号通稿形态。**少投第二维度的直接后果就是通稿。**
- 判定结论写进 MASTER.md 顶部一行，**必须带依据原话**：
  `> 品类判定：<结论> ｜ 依据 <PRD 或对话里的原话> ｜ 底座=ui-ux-pro-max ｜ 独一性与文案=<档位 / 未装配·降级>`

1) 读 PRD「视觉取值来源」与「设计稿依据」两行（`PRD-template.md` 预置）；取不到就到 `docs/项目交接.md`
   找 1·2 的风格三问结论。三处都没有 → 发一张选择卡问，不自选。

2) 跑情报库检索（脚本在 skill **自身目录**内，**必须拼绝对路径**，不得假设当前工作目录）：

   ```bash
   python -B ".qoder/skills/ui-ux-pro-max/scripts/search.py" \
     "<产品类型> <行业> <风格关键词>" --design-system --persist \
     -p "{项目代号}" --output-dir "<项目根>"
   ```

   - `--persist` 必须与 `--output-dir <项目根>` 同时出现，否则文件写进工具当时所在目录；
   - 解释器依次试 `python` → `py -3`；**不要用 `python3`**（Windows 商店别名，退出码 49 且无输出）；
   - 必带 `-B`，否则在库目录落 `__pycache__/*.pyc`，会被行尾完整性检查判为异常；
   - 解释器全不可用 → 按该 skill 自身规定降级直读 `data/styles.csv` + `colors.csv` + `typography.csv`，
     并在 MASTER.md 顶部注明「本次未走检索脚本」。**这是设计内路径，不是故障，不得报错停止。**

3) 🔴 **属主裁定优先于库的推荐**——这条不是客套，是正确性要求：
   库给的是候选与理由，而候选本身可能就是那份通稿默认（见 0) 的实测）。
   冲突时以属主为准，并在 `design-system/{项目代号}/MASTER.md` 顶部追加一行（与 0) 的判定行并列，两件事两条记录）：
   `> 属主裁定优先：<采纳项>；库推荐 <偏离项> 未采纳，理由 <一句话>`
   即便属主没给裁定、准备采纳库推荐，也必须先跑一遍第 4 步的通稿自检，过了才落 MASTER；
   没过就改并记「库推荐 <X> 判为通稿默认，已调整为 <Y>」。不得静默混用两套色板。

4) 产出 `design-system/{项目代号}/MASTER.md`，路径登记进 `profile.knownDocs`；**必须含四块，缺一即本步未完成**：
   **Color**（4-6 个命名十六进制 + 语义 Token 名）／**Type**（字族与角色）／
   **Layout**（一句话布局概念 + 每类页面一张 **ASCII 框线图** + 对齐指引）／**Principles**（这个项目"不像任何同类页"靠哪一点）。
   🔴 Layout 这块就是"布局谁负责"的答案：**每项目产一份，不把任何具体版式写进骨架模板**。
   写完对着 PRD 自问「这几块里有没有哪块换成别的产品名也照样成立」，成立就是通稿，改掉并说明改了什么。
   后续 P3 每页的 Token 取值一律引用这份 MASTER，不在页面里另起炉灶。

5) 把基调三项（风格名 / 主色与语义 Token / 字族搭配）用一行话给属主过目再继续，**不等口令**
   （属主要改会直接说；按 v9.8.0 R-B，这属过程提问，不属定稿闸门。
   ⚠️ 此处**刻意不照抄**上游设计 skill 的 "confirm with the client"——那一句会把机械推进重新变成等口令。）

6) 未装配创意实现能力（`frontend-design` 或等价件）→ **不报错、不卡住**：底座照做、自检照做，
   并在 MASTER.md 顶部记「独一性与文案=未装配·降级」，且在 P4 收口卡向属主**念出这一行**。
   🔴 不得让"降级"在交付话术里变成"已完成"。

### 步骤 P3：逐页做可点原型 + 单文件预览
- 每页能点开、异常分支能触达
- 🔴 **视觉六条底线**（缺任一即本步未完成；①-⑤ 由 `harness-verify` 的 `prototype_visual_floor` 机检，
  ⑥ 与下面整段文案纪律由 P4 收口卡承担）：
  ① 图标是真 SVG（图标库依赖或内联 `<svg>`，**禁 Unicode 字形/emoji 顶替**）；
  ② 字阶 ≥4 档（`--text-*` 语义 Token，非散写 px）；③ 间距阶 ≥4 档（`--space-*`）；
  ④ 圆角阶 ≥3 档（`--radius-*`）且海拔/阴影阶 ≥2 档（`--shadow-*`）——一套圆角糊所有层级、
     一个软阴影压所有卡片，是通稿页最贵的识别码；
  ⑤ 承载连续阅读的容器必须有 `max-width` 量纲约束（正文行长目标 <80 字符）；
     🔴 同一原型的 Vite 工程与 `预览.html` **必须同宽**，只在一处设上限按未完成处理；
  ⑥ 主/次按钮有可辨层级（全页只允许一个主色实心按钮承担本页主动作）
- **界面文案纪律**（机检不了，逐条进 P4 收口卡，不得只留在自查里）：
  · 链接与按钮文本**不得追加 `→`/`↗` 类箭头尾缀**；
  · 框架自身的过程性免责声明（如「原型占位，不涉最终视觉」）**不得出现在产品 UI 里**，这类话归 README 与收口卡；
  · 控件与导航按**用户视角**命名（用户管"通知"，不管"webhook 配置"），同一动作全流程同名，
    按钮写清点了会发生什么（「保存更改」不是「提交」）；
  · 假数据也是设计件：占位文案读起来假，整页就读起来假；
  · 眉题/编号/分隔线/标签必须**编码真实信息**，内容不是序列就不许用 `01/02/03`；
    禁全大写标签、禁标题里只挑一个词做强调色或斜体。
- 调试用控件（数据场景切换、登录态、异常承载入口）必须在视觉上与产品 UI 分离（异底色条/折叠面板），
  不得与产品导航同形同色——否则整页读起来像后台测试页，属主无法判断自己拒的是产品还是调试条
- `预览.html`：自包含单文件，禁引 CDN、禁 import 外部文件、禁发任何网络请求
  （否则 `file://` 双击白屏）——验收脚本见下方「预览.html 契约校验」

### 步骤 P4：自检与交接
- 构建、类型检查、lint 三项 0 错；路由数与页面清单 1:1；非单 HTML
- 执行 3 步同步，把原型工程路径回填环节 1·3 与环节 4 的输入位
- G1（原型可点）通过记录必须带截图证据文件路径，不接受「已完成」字样
- 🔴 **1·3 视觉收口卡（v9.11.0 新增，属主裁定，不可自证）**：贴 **3 张实拍截图**（首页面 / 最复杂页面 /
  一个异常态页面）+ 逐条回答下面 **8 问**，等属主点头才进环节 2：
  ① 首屏有没有大片空白；② 图标是不是真 SVG（放大看边缘，字符图标会露出字体锯齿/宽度不齐）；
  ③ 按钮分不分主次（本页主动作是不是唯一实心）；④ 正文有没有字阶（标题/正文/辅助文字一眼能分层）；
  ⑤ 调试条和产品 UI 分不分得开；
  ⑥ **P2.5 的投入度判定判对了吗**——本步按哪个档位做的、依据是哪句原话；属主若说"我要的是出彩不是稳"，
     则判定作废、回 P2.5 第 0 步重判并**重做已画页面**（不得只改注释）；
  ⑦ **界面文案读起来像不像真产品**（对 P3 文案纪律逐条核）：链接/按钮有没有挂 `→`/`↗` 尾缀；
     产品 UI 里有没有混进框架自己的免责声明；命名是不是用户视角；假数据读起来真不真；
     有没有非序列内容被加了 `01/02/03` 或全大写眉题；
  ⑧ 正文行长受不受控，且 **Vite 工程与 `预览.html` 两份是不是同宽**（不同宽即底线⑤未成立）。
  属主判不合格 → 记「**拒于第几问 + 属主原话**」进 `docs/项目交接.md`，改完重跑本卡。
  🔴 不接受 AI 自评「视觉已达标」；**也不接受用 `prototype_visual_floor` 的 PASS 代替本卡**——
  那条只判"在场"（声明了 4 个 `--text-*` 但页面不引用也能过），好看与否只有属主能判。

### 预览.html 契约校验（机器可判，不靠眼看）

交付前逐项自查（机器判定：`harness-verify` 检查项 `preview_self_contained`，FAIL 级；缺件时报
`SKIP:` 并写明未验证）：无外部 `src`/`href`、无外部 `import`、无 `fetch`/`XMLHttpRequest`。
脚本判不了的那半边仍靠人：断网后 `file://` 双击，页面必须完整渲染。
（校验逻辑在校验器里，不在文档里让人现抄——本库纪律：AI 不现写检查命令。）
## 产出契约（环节卡为单一契约源）

| 项 | 契约 |
|----|------|
| G2 定稿记录 | `docs/项目交接.md` 的「已完成项（附证据路径）」节（4·1 定稿时写入：设计计划三项确认 + 视觉判断通过 + 截图证据文件路径；无记录视为未定稿，禁进环节 5） |
| G3 还原基准 | `docs/spec/还原核对-{模块名}.md`（4·2 产出：逐页视觉判定 + 差异清单 + 用户裁定结果；环节 5 每改一个页面重复核对） |
| 产出物（必选） | `docs/spec/SPEC-UI-{模块名}.md`（设计 Token、页面清单、组件树、交互流程、四态流转） |
| 产出物（可选） | `references/ui/` 设计工程（4·1 产出工程时；与生产前端 `web/` 严格分离） |
| 产出物（可选） | 还原核对结论（4·2 产出：逐页视觉判定 + 差异清单 + 用户裁定，G3 基准） |
| 模板依赖 | `docs/harness-templates/SPEC-UI-template.md` |
| 归档位置 | `docs/spec/`（规范与决策记录）、`references/ui/`（设计工程） |
| 产出自检 | 每页有布局与组件归属；关键交互四态流转（加载/成功/失败/空）；公共组件复用关系明确；与 SPEC-FE 接口数据对应；4·1/4·2 两步 step_gate 全过 |
| 收尾 | 3 步同步（唯一规范：`.qoder/commands/live-refresh.md`；Backend-Only 项目本环节跳过，进展图标 ⊘） |

- 用户输入 `/ui-design`

## 前置条件

## 执行步骤

### Step 0: 前置确认（v9.0.0 单路线，无选路）

### Step 0.5: 应用类型检测

读取 `profile.appType`：

- **Backend-Only** → 本环节整体跳过：不执行 Step 1-6，3 步同步中环节 4 状态置 ⊘，产出物为空
- **Full-Stack / Frontend** → 进入 Step 1
- 未声明 → 暂停，回 `/create-proposal` Step0 补应用分类后重入

### Step 1: 读取输入（基于环节 1 冻结交互原型做视觉深化）

1. 读取 `docs/prd/PRD-{应用}-交互原型/` 工程（README 页面清单表 + 路由结构 + 四态实现）——**视觉深化的基准输入**
2. 读取统一 PRD Section4 交互流程：页面清单、用户流程、四态要求
3. 读取 SPEC-FE / ARCH 前端架构章节：技术栈、组件分层、状态管理
4. 如已有品牌约束（DESIGN.md / 既有组件库 / 风格要求），一并读取

### Step 2: 产出 SPEC-UI 文档

**模板来源**: `docs/harness-templates/SPEC-UI-template.md`
**产出路径**: `docs/spec/SPEC-UI-{模块名}.md`

必须包含：
- [ ] 设计 Token（色板/字阶/间距/圆角/阴影语义化命名，并标注取值来源）
- [ ] 排版规范（字阶系统、行高、对齐网格）
- [ ] 页面四态（加载/成功/失败/空）逐页定义
- [ ] 组件规范（按钮/表单/卡片/表格/导航的状态与变体）
- [ ] 响应式断点（移动/平板/桌面行为差异）
- [ ] 可访问性（A11Y）要求（对比度、焦点、键盘导航、ARIA）
- [ ] 「输入引用与保真度定位」小节：注明基于 Phase1 交互原型深化（模板已预置）

### Step 3: 检测内置设计能力可用性

检测当前环境是否具备 Qoder 内置设计类 skill（ui-designer / ui-ux-pro-max-design 等）：
- **可用** → 进入 Step 4 定稿与还原核对
- **不可用** → 降级：输出 SPEC-UI 文档 + 手工实现指引（含组件清单与验收标准），标注"待内置设计能力接入"

### Step 4: 定稿与还原核对（对应骨架 4·1 / 4·2）

本环节两步：宏步骤 4A = 骨架 4·1 定稿（含 G2 验收卡），宏步骤 4E = 骨架 4·2 还原核对与归档（建立 G3 基准）。旧版子步（A1-A6）已降级为 4A 的“执行细节”行。

#### 宏步骤 4A: 内置设计执行与定稿（骨架 4·1，含 G2）

**核心协议（5 编号子步）**：

1) **准备上下文**：IDE 文件树多选复制输入路径粘贴到对话框（勿粘贴 md 全文），确认文件路径可访问
2) **生成**：参考已带入文档编排内置 `ui-ux-pro-max-design` 生成前端 UI 设计工程输出到 `references/ui/`，先出设计计划（色彩方案/组件粒度/页面覆盖）待用户确认后执行
3) **产出 SPEC-UI**：docs/spec/SPEC-UI-{模块名}.md（含色彩/字体/间距/圆角/组件/交互六系统：设计 Token/排版/页面四态/组件规范/响应式断点/A11Y）
4) **迭代优化**：对话式修改（局部/风格/组件重做/批量四种模式，可多次执行，以用户视觉判断为准）
5) **预览验证**：references/ui/ 执行 npm install 与 npm run dev，4 项验证（无 TS 编译错误/响应式正确/颜色字号间距与 SPEC-UI 一致/组件交互流畅）后归档产物

**执行细节（旧子步降级）**：

| 旧子步 | 执行细节 | step_gate |
|--------|---------|-----------|
| A1 准备上下文 | IDE 文件树多选复制路径：PRD + SPEC-FE（+ 可选原型工程路径作视觉参考） | 文件路径可访问 |
| A2 调用内置 skill 生成 | 编排内置 `ui-ux-pro-max-design`，一次写明：产出路径（references/ui/ + SPEC-UI）+ 技术栈 + 风格关键词 + 响应式策略 + 页面清单 | 色彩方案/组件粒度/页面覆盖三项确认 |
| A3 确认执行 | 用户确认设计计划后开始生成 | 产物路径输出 |
| A4 迭代优化 | 局部/风格/组件重做/批量四种模式，可多次执行 | 用户视觉判断通过 |
| A5 预览验证 | `cd references/ui/ ; npm install ; npm run dev` | 4 项验证全过 |
| A6 产物归档 | 全流程在 Qoder 内完成，无需回流 | 路径命名符合规范 |

> 若项目已装配 ui-ux-pro-max 风格库，界面实现前先引用其风格/配色/字体决策结果。

**自检 step_gate（骨架 4·2 全迁入）**：文件路径可访问；色彩方案/组件粒度/页面覆盖三项确认；产物路径输出齐备；SPEC-UI 含设计 Token/排版/页面四态/组件规范/响应式断点/A11Y；用户视觉主观判断通过；4 项预览验证全过；路径命名符合规范。

#### 宏步骤 4E: 还原核对与归档（骨架 4·2，G3 基准建立）

**统一验收 step_gate（交付物契约：SPEC-UI + UI 工程 + 还原核对报告）**：

- `npm run build` + `tsc --noEmit` + lint 0 错
- 路由数 = PRD Section4 页面数
- 核心流程可完整点完
- 异常分支可触达
- 非单 HTML
- SPEC-UI 齐备且与工程一致
- 验证报告：预览 4 项结论（4·1）+ 逐页还原判定与差异清单（4·2）

**归档**：验证通过后归档产物（references/ui/ 与 SPEC-UI 就位）；**收口不通过时回到宏步骤 4A 对应子步修复后重验**；缺失部分回 Qoder 补齐（禁重开工具会话）。

**本地预览指引（建议字段附加）**：references/ui/ 执行 npm install 与 npm run dev 后浏览器逐页点看。
🔴 **不得写「或直接双击入口 HTML」**——「入口 HTML」全库无定义，而字面最像入口的 `index.html` 引的是 `/src/main.tsx`
（绝对路径 + 未编译 TSX），`file://` 下必白屏。原型侧唯一可双击件是 `预览.html`；环节 4 的 `references/ui/`
若要支持双击，其 vite `base` 同样必须是相对值（`'./'`），否则 `dist/index.html` 引的 `/assets/*` 会解析到盘符根。

**收口后附加编排：内置设计审查能力（可用时）**：

界面实现产出后，按以下顺序编排审查：
1. `design-system-capture` — 建立或核对项目设计系统（产出/校准 DESIGN.md）
2. `design-qa` — 设计验收（对照 SPEC-UI 与 PRD 交互流程）
3. `accessibility-review` — A11Y 审查（WCAG 导向）
4. （如涉及响应式）`responsive-design` / `component-library-alignment`

### Guardrails（最高优先级）

> **用户提供设计工程时（交互原型工程、UI 设计工程等任何形式；v9.0.0 单路线不再接 Figma 导出工程），前端实现必须与设计工程完全一致**，涵盖布局/视觉/组件层次/交互/动效/色彩/字体/间距等全部设计细节，**不得以任何理由（包括视觉相似度已达标）偏离设计工程**。此规则优先级高于本文件所有其他规则、编码规范及视觉相似度评分标准，并向下游环节 5 前端开发透传。

- NEVER：设计 Token 写成硬编码魔法值（必须引用 CSS 变量 / Tailwind theme，并与 SPEC-UI 的 Token 名一一对应）
- NEVER：还原核对迭代超过 5 轮仍继续（停止并上报残余差异，交用户裁定）
- NEVER：设计工程与生产前端工程混用同一目录（设计在 `references/ui/`，生产在 `web/`）

## 失败处理

| 失败场景 | 处理方式 |
|----------|----------|
| PRD Section4 / 交互原型工程缺失 | 暂停：PRD 缺失回 `/create-proposal` 补充；原型缺失执行 `/ui-design` 回补 |
| 应用类型为 Backend-Only | 本环节整体跳过，进展图标 ⊘，不产出 SPEC-UI |
| 内置设计能力不可用 | 降级为纯 SPEC-UI 文档流程，标注待补项 |
| 内置设计能力产出不可用/质量不足 | 降级为纯 SPEC-UI 文档流程 + 手工实现指引，SPEC-UI 顶部标注降级原因与待补项 |
| 视觉迭代达 5 轮仍有残余差异 | 停止迭代，输出残余差异清单交用户裁定，不带未裁定差异交付 |
| A11Y 审查发现 Critical 问题 | 阻断交付，修复后重审 |
| 与已有设计系统冲突 | 以 design-system-capture 核对结果为准，冲突走 ADR 决策 |
