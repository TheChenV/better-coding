# 编码前深度上下文收集

## 核心理念

> **不是你下指令 Agent 就干，而是 Agent 先彻底理解项目上下文，再反过来追问你。**
>
> 编码前最关键的步骤不是写代码，而是确保所有决策分支都已解决。
> 本 Skill 先深度阅读项目文档和代码库建立上下文，然后像资深工程师一样追问模糊点。
>
> 来源：对齐 mattpocock/skills 的 grill-with-docs 与 grilling 引擎——追问 + 共识落盘（CONTEXT/词汇本），避免方向错误。

## 触发条件

- 用户输入 `/precode-alignment`
- 开始新功能/新模块前需要深度对齐
- 需求描述模糊，需要追问澄清
- 用户说"帮我做 XX"但信息不足时

## 执行步骤

### Step 1: 深度阅读项目上下文

> **在追问之前，先自己搞清楚项目现状。**

**必须阅读的文件（按优先级）：**
1. `AGENTS.md` — 项目架构、命名规范、依赖规则
2. `docs/` 目录下的 Spec/PRD/ARCH — 需求和设计文档
3. `.qoder/rules/project-domain-glossary.md` — 领域词汇本（术语定义先查这里）
4. 项目配置文件（package.json / pyproject.toml / pom.xml / go.mod）— 技术栈
5. 目录结构 — 代码组织方式
6. 最近的 git log — 最近变更方向

**输出上下文摘要：**
```
项目上下文摘要:
- 技术栈: <从配置文件读取>
- 架构: <从 AGENTS.md 提取>
- 最近变更方向: <从 git log 推断>
- 已有 Spec: <列出相关文档>
- 已识别的模糊点: <列表>
```

### Step 2: 前沿式追问（Grill Phase）

> **设计树 + 前沿（frontier）：一轮问完当前全部未决决策点，每问附推荐答案，直到决策树走完。**
> 与 /create-proposal Step 1 共用同一套追问纪律（唯一定义点见该技能）：共识达成前不进入产出；事实自查不抛给用户；交互方式**全部遵循** create-proposal 的「交互方式纪律」（选择卡优先 / 分批≤4问 / **选项值可见：label=具体答案值、description=理由与量化影响** / 复杂确认用文本+收口卡 / 降级条款），以及全局规则 `.qoder/rules/ask-card-option-quality.md`。

**追问维度（按优先级）：**

1. **目标与价值** — 这个功能解决什么问题？不做会怎样？
2. **用户与场景** — 谁用？在什么场景下用？
3. **边界与约束** — 做什么？不做什么？技术/时间/兼容性约束？
4. **方案选择** — 有多种实现路径吗？偏好哪种？
5. **成功标准** — 怎么判断做完了？怎么判断做好了？

**追问规则（前沿式）：**
- 把待对齐事项映射为决策树，**一轮问完当前前沿**（前置已定的全部未决决策点），回答后重算前沿进入下一轮
- 每问编号 + 选择题 + 推荐答案 + 推荐理由；用户回"同意"即可推进；用户说"你来定" → 基于项目上下文给推荐并记入已决策；每个追问结合 Step 1 读取的项目上下文
- **先自查纪律**：可从代码/文档/AGENTS.md/词汇本推导的答案，以"初步结论 + 证据"呈现请确认，不抛问用户
- 不设硬性轮次上限；每轮问题数建议 3-5 个，预算用完不得自行补齐或直接开工；前沿为空且用户确认共识后才进入产出

**追问示例：**
```
基于我对项目的分析，有以下几个需要确认的关键决策：

❓ **Q1** - 这个功能需要新增 API 接口还是复用现有的 /api/v1/users？
➡️ 推荐复用现有接口（改动小）；如果需要新的响应格式则建议新增（证据：src/api/users.ts 现有结构）。

❓ **Q2** - 数据存储用现有的 PostgreSQL 还是需要引入 Redis 缓存？
➡️ 基于当前 DAU 规模（<10K），推荐先用 PostgreSQL，后续按需加缓存。
```

### Step 3: 输出对齐文档并回写词汇本

> **把所有追问的结果沉淀到 PROJECT-LIVE.mddocs/项目交接.md（或更新到 Spec 中）；共识术语当场写入词汇本。**
> 词汇本：`.qoder/rules/project-domain-glossary.md` —— 本次确认的术语逐条登记（术语/定义/英文标识/来源/确认日期）；同物多名提请用户裁定统一名。

```markdown
## 对齐摘要

### 决策记录（含被否决方案）
| # | 问题 | 决策 | 理由 | 否决的替代方案 |
|---|------|------|------|----------------|
| 1 | <问题> | <决策> | <理由> | <否决项与原因> |

### 约束确认
- <约束 1>
- <约束 2>

### 新确认术语（已写入词汇本）
- <术语> = <定义>

### 开放问题（阻塞项）
- <如有>

### 下一步
- <基于对齐结果，建议的下一步行动>
```

## 与 create-proposal 的分工（v5.1 定位澄清）

- `/precode-alignment`：**有代码库/文档基础的深度对齐**（grill-with-docs 定位），输出决策记录 + 词汇本回写；适合在已有项目上做新功能/变更前的对齐
- `/create-proposal`：**新需求轻量澄清**，输出 MRD/PRD（SDD 环节 1）
- 推荐流程（已有项目上的新功能）：`/precode-alignment` -> 对应环节指令（如 /create-module-spec、/implement-feature）

## 失败处理

| 失败场景 | 处理方式 |
|----------|---------|
| 项目无文档 | 基于代码结构推断，标注"推断-请核对" |
| 多轮仍无法对齐 | 需求本身需要重新梳理，建议回到 MRD/PRD（/create-proposal） |
| 用户拒绝回答 | 基于项目上下文做最佳推荐，标注"AI 推荐-请核对" |
