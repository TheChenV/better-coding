# 手动刷新指导中心与可视化面板

> **兜底说明**：本命令是阶段 A 装配到 `.qoder/commands/` 的项目级命令。若尚未装配、或 `/live-refresh` 无响应，直接说"刷新项目状态"（或"刷新可视化面板"），效果等同。
> **定位**：日常更新由 `/live-refresh` 的 5 类触发事件自动驱动；本命令仅在显示滞后、或用户想立即看到最新状态时手动兜底——本质是手动完整执行一次 3 步同步，不引入新机制。

## 执行步骤

1. 读取 `.qoder/harness-profile.json`
   - [ ] 文件不存在 → 说明 Harness 尚未初始化，提示用户先说"初始化 Harness"（执行阶段 A）；本次刷新到此结束

2. 按「同步执行细则」（见本文末节，**唯一规范源**）完整执行 3 步同步：
   步骤 1 更新四份产物 → 步骤 2 输出同步报告（来源记为 `manual-refresh`）→ 步骤 3 运行 `harness-verify` 并记录结果。
   报告的形状与排版**指针引用** `references/phase-a-checklist.md#A.5-⑤`（不复述规则）：结论先行、不写导语、树进代码块、机器口径进明细、未验证不得说成通过。
   细则中的推导规则、渲染纪律、拓扑判据与状态标注规则**逐条适用**，不得凭记忆简写。

3. 输出格式

   ```
   🔄 手动刷新完成（来源: manual-refresh）：
   - PROJECT-LIVE.md：[再生的分区清单 + 提示词手册状态变化]
   - PROJECT-LIVE.html：[拓扑/状态是否更新 + 更新依据（ARCH 文档/代码扫描/手册状态）；重推时列各图节点数（context/container/component）与各状态计数（待开发/进行中/已完成/存在Bug），无变化则写“无变化”]
   - harness-verify：PASS/FAIL
   💡 用浏览器打开 docs/PROJECT-LIVE.html 查看最新架构拓扑与技术栈（文件树可见，双击即开）
   ```

## 适用场景

- HTML 面板或提示词手册显示滞后于项目真实状态
- 手工改动了 `docs/arch/`、`docs/spec/` 或脚手架文件，希望立即反映到指导中心
- 升级回源（`/harness-upgrade`）后强制刷新一次全量状态

## 同步执行细则（3 步 · 唯一规范源）

> 本节由 `harness-continuous-sync` 规则整体搬入（v8.5.0）。
> 规则层只保留触发事件与执行边界；**过程式剧本放在这里按需加载**，
> 因为规则正文每轮全量注入上下文，而本细则只在真正执行同步时才需要读。

## 定稿 ≠ 同步 ≠ 进下一环节（v9.8.0，唯一定义点）

> 立项依据：v9.7.0 异地实测中，AI 把 1·1 提示词里「我说定稿锁定之前不要进下一步」泛化成"3 步同步也得等你说定稿"，于是交付物已落盘而三本账（profile / 手册 / 面板）全部滞后，且这份滞后对既有判据**完全隐形**——40 条判据全在比"账本 vs 账本"，没有任何一条比"交付物 mtime vs `sync.lastSyncAt`"。同一块提示词的执行契约其实无条件写着「完成后：3 步同步」，歧义出在话术，不在流程。

| 概念 | 成立条件 | 谁能挡住它 |
|---|---|---|
| **定稿锁定** | 该步交付物已落盘 **且** 该步「怎样算做完」清单全过 | **谁都挡不住**：它不是用户话语事件，沉默不是否决；用户直接复制下一环节提示词即视为追认 |
| **3 步同步** | 上一条成立即触发（或命中本文件任一触发事件） | 只有「阶段 A 首次同步 + 空项目」允许收窄渲染范围（见下），三步本身一条不删 |
| **进下一环节** | 用户给出下一步指令（复制下一段提示词 / 明说开始） | 用户没给指令前不得擅自动手——这条人工闸门**保留** |

- **定稿不是封条**：用户之后在对话里改需求 → 改完的交付物重过一次清单 → 重新定稿 + 重新同步。每次改动都要触发同步，不允许攒到"下次一起"。
- **需要用户裁定的分歧照旧问**（项目代号、实派名单、需求分歧选择卡、差异清单逐条裁定、分诊结论、部署前逐项确认、改规则与改技能）：那些是**内容与安全决策**，与"能不能定稿/要不要同步"无关。问没答完不得凭空产出交付物；但**一旦交付物落盘，同步不再有任何前置**。
- **未闭环风险的表达**：交付物带着未闭环的严重发现时照常定稿与同步，同时把风险写进文档头部状态行与 `profile.incidents`——风险要看得见，但不表现为把账本冻住。
- **`maturity.mrd` 的赋值规则（v9.8.0 补）**：此前该键全库没有任何规则写它（只有 `maturity_vs_disk` 反向校验它），AI 只能即兴。现定为：`docs/prd/` 下出现 `MRD*` 即 `true`，由 `hook auto-finalize` 按磁盘事实定点回写；文件被移走则由 `maturity_vs_disk` 判红并要求改回 false。⚠️ 环节 1 的**完成**判据仍是下表 `maturity.prd=true`，本条不新增第二事实源。

- **拓扑数据纪律**：数据来源仅限 `docs/arch/ARCH*` 文档 + 代码目录扫描，只绑定可推导事实，**禁止编造**；仅当本次触发事件涉及 `docs/arch/ARCH*` 产出/变更、`docs/spec/` 六件套产出、代码脚手架出现、提示词手册状态回填/新增 incident（影响状态徽标），或 `/live-refresh` 且上述来源较上次有变化时重新推导；无 ARCH 时三图保持模板初态的**最小示意**（context/container/component 各 2-4 个节点，节点与边一律带“示意”前缀，以免被误认真拓扑）
- **拓扑推导不可跳过（v7.2.0 强制）**：触发事件命中上述重推条件时，必须完整重推 `DIAGRAMS`，**禁止只更新其他数据而保留占位图**；重推完成后自查：`maturity.arch=true` 时 `DIAGRAMS` 中至少一段含真实节点与 `-->` 边（harness-verify Check 7a 以 FAIL 级兜底拦截拓扑空转）
- **状态标注推导规则（v7.4.0，节点 `.nst` 徽标四值）**：待开发（todo）= 默认态，手册该模块区块环节未启动（○）；进行中（doing）= 按“进展推导规则”该模块存在 ▶ 环节；已完成（done）= 该模块全环节 ✅；存在Bug（bug）= `harness-profile.incidents` 存在指向该模块的未关闭条目或最近校验相关 FAIL（**bug 优先级最高，与其他态并存时标 bug**）。多模块项目逐模块行映射，单模块项目继承整体进展；无依据一律待开发，禁止编造；状态变化（手册状态回填/新增关闭 incident）属于重推触发条件，必须同步刷新对应节点徽标，保证面板与提示词手册同源不漂移；外部系统/人员角色等无开发语义的节点可不带徽标（省略 `.nst`）
- **细化深度随信息成熟度递进（画满 ARCH 已有信息，不保守缩水）**：仅有 ARCH → 画全 context（角色/系统/外部依赖）+ container（前端/后端/数据/部署分组，标注通信协议）+ component 后端分层与 ARCH 已明确的模块；环节 3 产出 SPEC → component 细化到模块级（subgraph 分组 + API/数据表节点）；环节 1·步骤3 产出交互原型工程 / 环节 4 产出 UI 设计工程（`references/ui/`、`docs/prd/*-交互原型/`）→ 可选叠加 `uiArtifacts`/`prototypeProject` 节点（面板可选字段，向后兼容，无则不渲）；环节 5 产出代码 → 叠加真实目录结构扫描；环节 8 产出部署记录 → 补充部署边界（容器编排/端口/环境变量）
- 渲染正确性以 `build-panel.mjs` 的 **V8 数据块 lint** 为准（v9.3.0 起机器判，不再靠人眼）；仅在 V8 报点或用户明确要求时才用浏览器打开抽验。不得把 MD 专属内容（提示词/交接内容）写入面板。

**进展推导规则**（workflow 区状态行、进展图与步骤区块状态共用，唯一定义点在本规则）：进行中 = 第一个未完成环节（⊘ 环节不参与判定，直接看下一个），其后皆 ○。状态文案映射：✅=已完成、▶=进行中、○=待开始、⊘=跳过。

| 环节 | 完成判据 |
|------|---------|
| 1 需求 | `maturity.prd=true` |
| 2 架构 | `maturity.arch=true` |
| 3 模块设计 | `docs/spec/` 存在 SPEC（扁平文件或 `NNN-slug/` 目录均认） |
| 4 UI 设计 | 存在 SPEC-UI*；`techstack.frontend` 为空 → ⊘ |
| 5 开发实现 | 前置：techstack=true 且 SPEC 就绪；完成：存在 docs/spec/联调记录-* 或 docs/test/spec-*-测试报告.md（下游产物反推，启发式，需在文中保留该标注） |
| 6 联调 | 存在 docs/spec/联调记录-* |
| 7 集成测试 | 存在 spec-*-测试报告.md（docs/test/） |
| 8 部署上线 | 存在 docs/spec/上线记录-* |

**提示词渲染纪律**（渲染 workflow 区提示词时强制遵守）：
- 以 `.qoder/briefing-skeletons.md` 的环节骨架 + 参数绑定表为准，**事实绑定渲染**：环节 1·1 保留用户占位符 `{一句话想法}`；其余步骤由 AI 按前序步骤真实产出渲染完整提示词（包含已确定的技术栈/路径/模块名等事实信息），不再是固定替换几个占位符
- 参数无来源 → 保留 `{占位}` 并标“待检测”；**禁止编造，禁止把需求内容演绎进提示词文字**
- 渲染后逐参数对账：每步骤渲染完成后按骨架该步骤「参数清单」逐项核对——每个参数必须真实绑定或保留 `{占位}` 并标”待检测”，二者必居其一；静默丢弃参数视为渲染失败；**权威值已在场却仍留占位同样视为渲染失败**（判据 `binding_stale`；哪些参数属”权威已在场”由骨架『参数绑定表』第 4 格「机检」点名，细则见下方「应用清单与已可绑必当轮绑」）
- 含义说明/注意事项照搬骨架，不自由改写
- 提示词渲染为独立代码框（```text```）——区块中唯一可复制内容，**整块逐字不删段**；执行契约中的内部编排协议（迭代常量、subagent 派发、Phase 编号、Gate 级别、profile 字段写入、内部工具与 skill 名）禁止进入提示词；注意事项与自检标准须取自 step_gate 的**用户可核对子集**并用用户语言表达；命中骨架『用户语言禁词表』（白名单除外）即渲染失败
- 已完成环节的提示词区块保留（状态标✅，供回溯与复跑）
- 半自动参数（模块名/功能名等）推导后须经用户确认；初态为环节 1 进行中 + 其余环节待开始（用户唯一输入 = {一句话想法}）
- **步骤区块与 token**：每步骤 = 独立区块，标题格式 `#### {emoji} N·k {步骤名}`（N=环节号、k=步骤号、`·`=U+00B7 中点）；token `N·k` 置于标题中供 harness-verify 按标题定位（同命令多步骤如 1·1 / 1·2 均 `/create-proposal` 不再碰撞）；标题 emoji 必须与状态一致（✅=已完成、🔄=进行中、⬜=待开始、⏭️=跳过）
- **建议字段纪律**：手册侧只渲两处人话建议——环节级「本环节建议」（引用块）与步骤级「建议怎么用」；骨架「形态建议」三元组（执行载体 连续执行/交互确认｜协作形态 多专家并行/单会话｜窗口 延续/新开）留在执行契约、不渲进手册，**禁止包含模型选型建议**（“强推理模型”/“轻快模型”等一律不渲染）；step_gate 全量与 next_hint 原文仍禁止渲染进提示词正文（next_hint 的下一步衔接以用户语言进入「做完之后」收尾行）
- **复数单元拆区块（仅产出型步骤）**：骨架标注 `[复数单元]` 或拆行规则标注“产出型”的步骤（环节 3/5/6/7 的产出型步骤），按单元清单（ARCH 推导 / docs/spec/ 目录）**按批次/模块拆区块并编号**（批次 1/N 或 模块 1/N…；环节 3 为批次=依赖拓扑分层，默认单批单区块；拆批例外——单批 N>5 或批内强耦合按依赖子图拆批，深度 review 可退回按模块逐区块渲染），每区块提示词绑定该单元参数、独立代码框可复制；**校验型步骤折叠为单区块**、参数用 `{模块清单}` 多值（清单型合并渲染）；清单标“待确认”支持用户回复调整或选择卡确认；单元未确认时先按推导清单渲染并整体标“待确认”；拆出的每一区块同样适用逐参数对账纪律与步骤 token 纪律
- **渲染格式纪律**：提示词整块渲染为独立代码框（```text```，区块中唯一可复制内容），八个标签段的归属同上条纪律；已完成环节/步骤的区块保留（状态标✅，供回溯与复跑）；PROJECT-LIVE.md 正文**禁止裸 `~`**（GFM/cmark-gfm 单波浪号即删除线），区间一律用 `-`，确需 `~` 必须用反引号代码跨度包裹

#### 双写者与整文件重写（v9.9.0 新增）

`.qoder/harness-profile.json` 现在有两个写者：AI（本细则的同步）与 `hook auto-finalize`（交付物一落盘就登记磁盘事实）。规矩：
- AI 编辑 profile 前**必须紧邻重读**（不要用几十秒前读到的内容定位），`0 occurrences found` 一次即重读重试；
- **禁止整文件重写 profile**——旧快照会把 hook 写好的 `maturity.mrd/prd=true` 静默抹回 false；该方向由 `maturity_vs_disk` 的反向断言兜（v9.9.0）；
- hook 侧刻意只写 `maturity.mrd/prd` 与 `history`，不写 `knownDocs`/`sync.lastSyncAt`/footer/面板/手册（坏处逐条见 `.qoder/hooks/hook-registry.md`）。

#### footer「最近校验」的三态（v9.9.0 补，此前无权威值时没有合法写法）

`sync.lastVerify` 只能由 stop-verify hook 回写。因此 footer 只有三种合法取值：有值 → 逐字写该 `status`；**无值 → 只能写模板初值 `待执行`**；不得自创"最近校验: FAIL（1 项 …）"这类带结论的说明句（那会同时踩 `live_profile_drift` 的"结论无权威来源"分支）。未验证的真相写进同步报告正文与 `history`，不写进机械位。

#### 应用清单与「已可绑必当轮绑」（v9.10.0 新增）

**应用清单的唯一权威源 = `profile.project.apps`**，元素形状 `{ "name", "type", "source" }`：

- `name`＝应用名，会进 `docs/prd/PRD-{应用}.md` 文件名 ⇒ 不得含空格与 `/ \ : * ? " < > |`，数组内唯一；
- `type` ∈ `Backend-Only` / `Full-Stack`，**只有这两个值**（与 create-proposal Step 0 的应用分类同一枚举）；
- `source`＝出处（例：`docs/prd/MRD-notehive.md §4.3，2026-09-13`）——P4 要求"可推导项必须标来源"，留空即判红。

写入时机：1·1 的 Step 0 应用分类（`/create-proposal`）产出即写。**单应用也必须写成一条**，不得退回"只有一个标量 `appType`、多应用无处安放"的旧形状。
`appType` 仍是手册分支折叠的依据（步骤 1 渲染 workflow 区时读它），所以单应用场景两者必须逐字相同（不一致由 `apps_single_source` 判红）；多应用场景 `appType` 不再是权威，折叠逻辑本批未改。
⚠️ 旧文档里出现过的 `appTypes: { "应用名": "类型" }` 从未实现、也没有任何读者，一律改用 `apps`。

**提示词值段只准照抄应用名。**真环境反例（Work009 把同一事实在一页里写了四遍、四种措辞）：
`应用清单 notehive（Full-Stack，单应用）`｜`（本期应用清单唯一，参数 {应用} 已绑定为 notehive）`｜`notehive（Full-Stack，唯一应用，故本步不跳过）`｜`（本应用清单只有 notehive 一个…）`。
分类与"这一步做不做"属于 MRD 那一章的内容；抄进提示词值段就是第二事实源（MRD 一改，四处同时说谎，而且四处措辞各不相同，谁都发现不了）。值段后面的括号说明必须与骨架模板那行**逐字相同**，被换成自创句子即判红。

**参数对账的三义务**（第 ③ 条是本批新增）：① 每个参数要么绑定、要么保留 `{占位}` 并标"待检测"；② 静默丢弃参数＝渲染失败（`prompt_params`）；③ **权威值已在场的参数必须当轮绑掉，不得以下游步骤"还没到"为由留占位**（`binding_stale`）。
哪些参数受 ③ 约束：骨架『参数绑定表』第 4 格标 `机检` 的那些——它与 `harness-verify.mjs` 里的 `READY` 谓词表**双向对账**（改表不改代码、或代码加了谓词不登记表，都会当场判红）；标 `未纳入` 的参数暂时只受 ①② 约束。
下游步骤里 `docs/arch/ARCH-{项目代号}.md` 这类"已经能填却还留着花括号"的位置，就是 ③ 要抓的形状：用户复制那段提示词时得自己填路径，等于把手册 `:36` 承诺的"自动绑定参数"退回到手工。
