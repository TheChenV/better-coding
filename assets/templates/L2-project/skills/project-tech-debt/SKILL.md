# 技术债务清理流程

> **使用说明**：根据项目实际情况定制。`【__名称__】` 为必填占位，`【__名称__，可选】` 为选填，`【已预填：xx，请核对】` 为 AI 预填项。

## 触发条件

当项目积累的技术债务影响到开发效率或系统稳定性时，按计划触发清理。

## 技术债务分类

| 类别 | 描述 | 优先级判定 | 示例 |
|------|------|-----------|------|
| 架构债务 | 违反分层规则、循环依赖 | 高（影响扩展性） | 【__Controller 直接调用 Repository__】 |
| 代码债务 | 重复代码、过长方法、过深嵌套 | 中（影响可维护性） | 【__500 行的 God Class__】 |
| 测试债务 | 缺少测试、测试不稳定 | 中（影响质量信心） | 【__核心模块无单测__】 |
| 文档债务 | 文档缺失、过时 | 低（影响协作效率） | 【__API 文档与实际不符__】 |
| 依赖债务 | 过时依赖、已知漏洞 | 高（影响安全性） | 【__使用已 EOL 的框架版本__】 |
| 配置债务 | 硬编码配置、环境混乱 | 中（影响运维效率） | 【__数据库地址写死在代码中__】 |

## 执行步骤

### Step 1: 债务盘点

- 扫描代码中的 `TODO`、`FIXME`、`HACK`、`XXX` 标记
- 检查架构合规性（对照 `project-layer-dependency` 规则）
- 检查测试覆盖率报告：【__覆盖率工具/报告地址__】
- 检查依赖漏洞：【__mvn dependency-check / npm audit__】
- 收集团队反馈的痛点
- 输出：技术债务清单（表格形式）

债务清单模板：

| # | 类别 | 描述 | 位置 | 影响 | 优先级 | 预估工时 |
|---|------|------|------|------|--------|----------|
| 1 | 【__架构__】 | 【__描述__】 | 【__文件/模块__】 | 【__影响说明__】 | 【__P0/P1/P2__】 | 【__xh__】 |

### Step 2: 优先级排序

排序原则：
1. **安全风险** > **架构合规** > **开发效率** > **代码美观**
2. 高频修改区域的债务优先（热点代码）
3. 阻塞新功能的债务优先
4. 投入产出比高的优先（小改动大收益）

输出：排序后的清理计划（按迭代分配）

### Step 3: 制定清理方案

对每项债务制定具体方案：

```markdown
## 债务项：【__债务描述__】

### 现状分析
- 当前代码：【__问题代码位置__】
- 问题本质：【__为什么这是债务__】
- 影响范围：【__哪些模块/功能受影响__】

### 清理方案
- 目标状态：【__清理后应该是什么样__】
- 实施步骤：
  1. 【__步骤1__】
  2. 【__步骤2__】
- 风险点：【__可能的风险__】
- 回滚方案：【__如何回滚__】

### 验证标准
- [ ] 【__验证条件1__】
- [ ] 【__验证条件2__】
```

### Step 4: 安全重构执行

**核心原则：重构不改变外部行为，每次只做一种类型的变更。**

执行规则：
- 每次 PR 只处理一项债务（原子性）
- 重构前必须有测试保障（无测试先补测试）
- 小步前进：大重构拆分为多个小步骤
- 每步可编译、可运行、可回滚
- 重构与功能开发不在同一 PR

执行顺序：
1. 补充/完善测试（建立安全网）
2. 执行重构（保持测试绿色）
3. 验证行为不变（测试全部通过）
4. 清理残留（删除废弃代码）

### Step 5: 验证与回归

- [ ] 所有现有测试通过（零失败）
- [ ] 新增测试覆盖重构区域
- [ ] 编译零 Warning
- [ ] 性能无退化（对比重构前后关键指标）
- [ ] 接口行为不变（契约测试通过）
- [ ] 相关功能冒烟测试通过

### Step 6: 防复发机制

- 评估是否需要新增/更新 Rule 防止债务再生
- 评估是否需要添加 Hook 自动检测
- 更新 AGENTS.md 中的架构说明（如架构变更）
- 在 Code Review 检查清单中增加对应项

### Step 7: 记录与归档

- 更新技术债务清单（标记已解决）
- 记录清理经验（可复用的重构模式）
- 更新相关文档
- 通知团队变更内容

## 输出物

- 技术债务清单（更新版）
- 重构代码 + 测试
- 防复发 Rule/Hook（如需要）
- 清理经验记录

## 节奏建议

| 项目阶段 | 建议节奏 | 说明 |
|----------|----------|------|
| 快速迭代期 | 每个迭代 10% 时间 | 只做高优先级、小范围清理 |
| 稳定维护期 | 每个迭代 30% 时间 | 系统性清理，含架构调整 |
| 版本间隙 | 专项清理周 | 集中处理积累的大项债务 |

## 禁止事项

- ❌ 禁止无测试保障的重构
- ❌ 禁止在功能开发 PR 中夹带重构
- ❌ 禁止一次性大规模重写（风险不可控）
- ❌ 禁止清理"看不顺眼"但无实际影响的代码（过度重构）
