# 调试能力补丁：反锚定策略与经验沉淀

> **定位**：v4.0.0 起，系统化调试的主体能力由 **Qoder 内置 `systematic-debugging` skill** 承担（本库不再复制同名 skill）。
> 本文档保留原 better-coding 版本中内置版未覆盖的两块特色内容，作为补丁在调试场景叠加使用。
> **使用方式**：进入调试流程时，先执行本文档的"反锚定预检"，再走内置 systematic-debugging 流程；修复完成后执行"经验沉淀"节。

---

## 一、反锚定策略（调试前预检）

> 来源：Harness 课程第 9 课 —— "大部分问题是 Agent 的问题，不是 AI 的问题"

在开始调试前，先执行反锚定检查：

1. **只带问题，不带方案** — 先描述"预期行为"和"实际行为"的差异，不要急于猜测原因
2. **要求至少 3 个假设** — 禁止锚定第一个假设，按验证成本从低到高排序
3. **反向提示** — 如果已经有一个"很确定"的原因，强制自己再想 2 个替代解释
4. **从第一性原理出发** — 不要基于"上次类似问题是 X 导致的"来推断，每次从零分析

**核心：问题的权重 > 方案的权重。**

### 上下文衰减熔断

- **调试时间超过 2 小时无进展 → 必须暂停**，换视角或寻求结对调试（上下文衰减会严重降低调试效率）
- 长会话中若出现"重复行为/方案锚定/回答变泛"信号，先执行 `/context-handoff`（context-handoff）交接后开新会话继续

## 二、经验沉淀（修复完成后执行，Ratchet 入口）

**将调试过程记录为可复用的知识：**

```markdown
## Bug Report: <标题>
- 根因: <一句话>
- 修复: <修改了什么>
- 教训: <未来如何避免>
- 关联测试: <新增的测试文件/用例>
- 模式识别: <这类 Bug 的共性特征，便于未来快速定位>
```

**沉淀行动（按优先级）**：

1. **通用问题** → 考虑添加 lint 规则或编译检查防止再犯
2. **项目特有约定** → 写入 `.qoder/harness-profile.json` 的 `incidents[]`（type: bug），并生成规则变更提案：
   - 提案经用户确认后落盘为 rule（frontmatter 携带 `causedBy: INC-xxx`）
   - 或更新 AGENTS.md / 相关 Rule
3. **依赖问题** → 记录到依赖审计清单（dependency-management 规则）
4. **偶发经验** → 记录到 Memory（如被引用 ≥5 次，由 retrospective 提议升级为 Rule）

> **纪律**：每条因调试而新增的规则，必须能追溯到 incidents[] 中的一次真实失败 —— 这是 Ratchet 机制的核心（"好规则文件的每一行都应能追溯到一次具体失败"）。
