# SDD 门禁检查清单（Gates Checklist，分级版）

> **定位**：本清单是 SDD 各阶段门禁**唯一权威的可执行形态**（原 9 道 gate 已合并为 3 道主门禁）。
> 9.0.0 起 modes 与 pipelines 的参考 yaml 已作为死码删除，本清单不再有上游副本；各阶段收尾 skill 实际引用的门禁依据就是这里。
> **审查方式**：门禁由 **AI 自检 + 用户确认** 完成，不设额外审批角色。
> **用法**：各阶段收尾 skill 在"追加同步步骤"前先逐条核对对应门禁；未通过 → 回退修改（on_fail 语义）。
> **环节口径**：门禁覆盖 **9 个 SDD 环节**（Hooks 为横切基础设施，不占环节编号，见附录 H1-H5）。

## 文档职责边界矩阵（强约束，禁止越界）

> 吸收 AINative `explore.md` 文档职责边界矩阵并扩展到 SPEC 层。写每一节都要对照本矩阵，**越界内容一律改写为前向引用**（如"详见 ARCH 中的性能 SLA"）。这是 spec 门禁"跨文档一致性"的核心判据。

| 交付物 | 应该写（本层职责） | 严禁写（属下游文档，改前向引用） |
|--------|--------------------|----------------------------------|
| **MRD** | 市场机会、目标用户、价值主张、产品组合（名称+类型+目标用户）、阶段方向、方向级规模目标、业务风险 | 模块拆分、架构分层/边界/依赖、技术指标（P99/QPS/SLA）、系统设计、数据模型、API 契约 |
| **PRD** | 功能列表、模块拆分、用户故事（US-{APP}-{NNN}）、交互流程、验收标准、业务规则 | 架构设计、技术选型、部署拓扑、详细接口字段、性能 SLA 量化 |
| **ARCH** | 系统架构、分层、模块边界/依赖、技术栈、性能 SLA（P99/QPS）、容量规划、安全架构、部署拓扑 | 市场分析、商业模式、用户研究、功能优先级 |
| **SPEC-BE** | 后端分层职责、数据模型、异常场景四类覆盖、幂等/限流/降级、事件 Schema、API 实现细节 | 市场需求、前端组件实现、UI 视觉规范（属 SPEC-UI） |
| **SPEC-FE** | 前端独有决策：组件划分、状态管理、路由、页面-模块-US 映射 | 与后端共用的契约正文（引用 SPEC-API）、通用架构（属 ARCH） |
| **SPEC-UI** | 界面结构、交互四态流转、失败态/空态、页面布局与组件归属、设计 Token | 业务逻辑实现、数据模型（属 SPEC-BE）、API 字段（引用 SPEC-API） |

## 门禁 4 级挂载模型（融合 AINative 三层验证 + better-coding 三道主门禁）

> 门禁不是单点，而是自上而下 **4 级挂载**。三道主门禁（L3）由下三级逐层支撑；每级失败均触发对应 on_fail 回退。

| 级 | 名称 | 挂载字段 | 触发时机 | 来源 |
|----|------|----------|----------|------|
| **L0** | 前置条件检查 | 环节 `trigger` | 进入环节前：确认上游交付物已冻结、输入文档齐备（v9.8.0：冻结由交付物落盘 + 该步清单全过成立，不等待用户口令） | AINative 三层验证·第 1 层 |
| **L1** | Step 级检查点 | 步骤 `step_gate` | 每个步骤完成后即时验证（格式、完整性） | AINative 三层验证·第 2 层 |
| **L2** | 环节质量门禁 | 环节 `phase_gate` | 环节全部步骤完成后综合评审（交叉验证、一致性） | AINative 三层验证·第 3 层 |
| **L3** | 三道主门禁 | 环节 `main_gate` | 门禁收口点（spec / implement / release 三选一） | better-coding 特有 |

> **上下文质量决定代码质量**：L0 前置检查把“上下文完整性”纳入编码启动前置条件——业务规则已从业务模块说明提取、实体关系已从架构文档同步、API 接口签名已引入；上下文不完整则不启动编码（质量左移）。

> **v8.4.0 提示词与门禁的关系**：step_gate 仍为全量检查项的唯一存放地（骨架子块内）；但每个步骤的提示词代码框必须携带其**用户可核对子集**，以用户语言写在「自检标准」段（并遵守骨架『用户语言禁词表』）——目的是让用户不打开骨架也能判定“什么算做完”，而不是把全量阈值复制进提示词。机器侧由 harness-verify Check 7e/7f 拦住，本清单的门禁定义本身不改。

## 规模分诊（先定路线，再走门禁）

| 变更规模 | 路线 |
|----------|------|
| ≤5 个文件的改动 | 走 `/quick-spec`，免门禁全链 |
| 常规功能 | 走下方 3 道主门禁（spec → implement → release） |
| 中大型特性 | 3 道主门禁 + 附录「中大型特性追加检查」 |

> 来源：v8.2.0 步骤压缩（旧环节 7 全链 6 步分步的合并模式条款迁入，对应新 7·1/7·2）
- **环节 7 小项目合并模式**：小项目（≤2 模块或 ≤5 接口）——测试计划+执行+报告可并为单条 `/run-tests` 提示词一次完成（生成计划+执行+报告+GO/NO-GO 建议一并产出），免走 7·1/7·2 全链分步；合并的只是执行步骤，implement 门禁全部判据不豁免。

## 门禁覆盖范围：9 环节 → 3 道主门禁映射

> 门禁覆盖范围由 8 环节扩展为 **9 环节**；每环节挂载到唯一一道 L3 主门禁，环节 9 为局部回环。

| 环节 | 名称 | L3 主门禁 | 说明 |
|------|------|-----------|------|
| 环节 1 | 需求澄清 | **spec** | idea→MRD→PRD→交互原型（Full-Stack） |
| 环节 2 | 架构设计 | **spec** | C4 双图 + 选型 ADR + 部署容量 + 红队冻结 |
| 环节 3 | 模块设计（复数） | **spec** | 逐模块 SPEC 六件套 + 一致性/完备性审核 |
| 环节 4 | UI 设计（路径分叉） | **spec** | 产出 SPEC-UI，作为 **implement 前置输入**（Backend-Only 跳过 ⊘） |
| 环节 5 | 开发实现（路由+复数） | **implement** | 后端 BE / 前端 FE 五阶段渐进 |
| 环节 6 | 联调（复数） | **implement** | integrate-modules：Mock→真实调用 + 契约测试循环 |
| 环节 7 | 集成测试（复数） | **implement** | API+E2E，覆盖率≥80%，五轴审查 + GO/NO-GO |
| 环节 8 | 部署上线 | **release** | 上线检查清单 + 部署执行 + 健康检查 + 上线记录 |
| 环节 9 | 迭代回顾（分支） | **局部回环** | 按 S0 分诊挂 implement（缺陷/重构）或 spec（新功能回环节 1 全链） |

- **spec 门禁** = 环节 1-4；**implement 门禁** = 环节 5-7；**release 门禁** = 环节 8；**环节 9** = 局部回环（按分诊挂 implement/spec）。
- 横切：**Hooks 配置**嵌入环节 1-9 所有环节的 Agent 生命周期，不占环节编号（见附录 H1-H5）。

**责任 skill**：/create-proposal、/create-architecture、/create-adr、/create-module-spec、/ui-design ｜ **失败处理**：带反馈重试（≤2 次）

## 门禁 2：implement 门禁（合并原实现/测试/评审门禁）

**覆盖环节**：环节 5-7（环节 9 缺陷/重构分支局部回环同挂本门禁）｜ **4 级挂载**：L0 SPEC/上下文冻结且可运行 → L1 每步骤 step_gate（编译/Lint/单测即时验证）→ L2 环节 phase_gate（覆盖率/契约 0 diff/无 Flaky）→ **L3 implement 门禁**

  > 来源：v8.2.0 步骤压缩（旧步骤 7·5 迁入）

## 附录：Hooks 配置验证清单（H1-H5）

> **定位**：Hooks 是嵌入环节 1-9 所有环节 Agent 生命周期的"第 0 层"横切质量保障，**非独立 SDD 环节、不占环节编号**；作为本清单附录 + `/check-project` 增强。
> **事件选型（先选对事件再写实现）**：`PreToolUse`＝拦截器场景（工具执行前校验，可阻断 exit 2；危险命令/敏感参数）｜`PostToolUse`＝副作用+反馈场景（执行后触发，feedback 回喂 Agent；lint/format/自动测试）｜`UserPromptSubmit`＝输入侧拦截/审计（每次 prompt 提交触发，可记日志/可阻断；敏感信息检测/prompt 审计）｜`Stop`＝完成通知（任务完成触发，无法阻断；桌面通知/完成日志）。
> **跨平台口径（v9.0.0 起）**：三平台只有一条 hook 命令 `node .qoder/scripts/harness.mjs hook <name>`，不存在平台分支执行器；Windows 侧表现已实测，macOS / Linux 侧结论以该项目实际实测为准（未实测时须显式标注"未实测"，不得用"Node 跨平台所以一致"替代）。

| # | 检查项 | 门禁判据（step_gate） |
|---|--------|------------------------|
| **H1** | 清单设计（事件选型） | Hooks 清单覆盖质量/安全/规范场景；每场景已匹配正确事件类型（PreToolUse/PostToolUse/UserPromptSubmit/Stop）；已声明 exit 0 放行 / exit 2 阻断策略 |
| **H2** | 编写 hook 实现 | 实现落在 `.qoder/scripts/harness.mjs` 的 `hook <name>` 分支（不新增独立脚本文件）；从 stdin 读整段 JSON 并解析 `tool_input.command`；exit 码语义正确（0 放行 / 2 阻断并将 stderr 回喂 Agent）；危险命令模式匹配完备 |
| **H3** | settings.json 绑定 | hooks 字段格式正确；事件与 matcher 绑定准确；`command` 三平台同一条 `node .qoder/scripts/harness.mjs hook <name>`（无平台分支执行器） |
| **H4** | 逐 hook 触发验证 | 在 chat 提交触发 prompt，逐 hook 逐场景验证；指定场景能正常触发、结果符合预期、不同 OS 表现一致 |
| **H5** | 宁缺毋假处置 | 未触发/结果异常时排查工具输出（如 eslint）是否干扰插件 feedback；调整脚本或降级为告警；**无法稳定触发的 hook 一律移除，宁缺毋假**（假阳性/假阴性清零） |

- **Hooks 门禁（phase_gate）**：能力范围审核（覆盖质量/安全/规范 + 功能合理）+ 触发效果审核（正常触发 + 结果符合预期 + 跨 OS 一致）；两类均过方视为 Hooks 配置完成。

## 附录：模块一致性审核矩阵

> 环节 3（模块设计）与环节 6（联调）的核心门禁，对应环节 3 的 S2（模块内）/S4（模块间）与需求追溯。任一维度过不了 → 回退修改对应 SPEC。

| 维度 | 审核内容 | 判据 |
|------|----------|------|
| **模块内一致性** | 单模块 SPEC 六件套（BE/FE/API/DDL/TEST/tasks）内部自洽 | 字段命名统一；异常场景四类（正常/异常/边界/并发）覆盖；幂等/限流/降级已设计；DDL 与数据模型对齐；测试用例覆盖本模块全部 P0/P1 US |
| **模块间一致性** | 跨模块契约对称、依赖无环 | API schema 对称（Provider＝Consumer 引用同一份 SPEC-API，0 diff）；共享 DTO/枚举定义一致；事件 Schema 生产端与消费端匹配；跨模块依赖无循环 |
| **需求-模块一致性** | PRD 需求到模块的双向可追溯 | 每个 PRD US 映射到 ≥1 个模块 SPEC；追溯表完整（US → SPEC → DDL → API）；无孤儿模块（无对应 US）、无遗漏 US（无对应模块） |
